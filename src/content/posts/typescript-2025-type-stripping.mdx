# TypeScript 2025: 타입 제거(Type Stripping) 시대의 도래

## 개요

"TypeScript는 컴파일이 필요한 언어"라는 문장은 이제 절반만 사실입니다. 실행 시점에서는요. Node.js가 `.ts` 파일의 타입 주석을 그냥 지우고(제거하고) 실행하는 기능을 정식 배포에 포함하면서, 간단한 스크립트나 백엔드 서버를 "빌드 단계 없이" 돌리는 흐름이 현실이 됐습니다. 이를 **타입 제거(type stripping)**라고 부릅니다.

이 글은 Node의 타입 제거가 실험 플래그에서 기본값이 되기까지의 타임라인, "지울 수 있는 문법(erasable syntax)"이라는 제약의 의미, TypeScript 5.8의 `--erasableSyntaxOnly`, 그리고 tsx·Bun·Deno와의 비교와 ts-node 마이그레이션까지 정리한 실무 노트입니다. 최근 몇 달 사이 블로그와 사이드 프로젝트의 실행 스크립트를 모두 이 방식으로 바꾸며 겪은 것들입니다.

## 배경: 왜 .ts를 바로 실행하고 싶은가

TypeScript의 타입은 컴파일 타임에만 존재하고 런타임에는 사라집니다. 그런데도 지금까지는 실행을 위해 tsc로 JS로 내보내거나 ts-node/tsx 같은 로더를 끼워야 했습니다. 이 과정은 학습 초기에는 자연스럽게 받아들이지만, 프로젝트가 늘수록 비용이 됩니다.

- **빌드 산출물 이중 관리**: `src`의 `.ts`와 `dist`의 `.js`, 소스맵, watch 프로세스가 늘 따라다닙니다.
- **도구마다 설정이 다름**: ts-node의 CommonJS/ESM 설정 이슈는 오랜 진통이었고, 새 팀원 온보딩의 첫 걸림돌이었습니다.
- **짧은 스크립트에는 과잉**: 서버 몇 줄 돌리는 데 컴파일 파이프라인을 세우는 것은 무겁습니다.

핵심 통찰은 "타입만 지우면 되는 코드라면 트랜스파일은 불필요하다"는 것입니다. 타입 주석 제거는 구문 분석 후 주석을 빼는 수준의 가벼운 작업이라, 런타임에 내장해도 부담이 없습니다. Node가 택한 방식이 정확히 이것입니다.

## 타임라인: 실험 플래그에서 기본값까지

1년 남짓의 변화를 날짜로 정리하면 다음과 같습니다.

- **2024년 8월 — Node 22.6.0**: [실험적 TypeScript 지원](https://nodejs.org/en/blog/release/v22.6.0)이 `--experimental-strip-types` 플래그로 처음 도입됐습니다. Marco Ippolito의 작업으로, 타입 주석을 제거해 `.ts` 파일을 실행합니다. 같은 해 22.7.0에는 변환이 필요한 문법까지 다루는 `--experimental-transform-types` 플래그가 추가됐습니다.
- **2025년 1월 — Node 23.6.0**: [해당 기능이 언플래깅됐습니다](https://nodejs.org/en/blog/release/v23.6.0). Current 라인에서 플래그 없이 `.ts`가 실행됩니다.
- **2025년 7월 — Node 22.18.0**: [LTS 라인에서도 기본 활성화](https://nodejs.org/en/blog/release/v22.18.0)됐고, [공식 문서의 변경 이력](https://nodejs.org/api/typescript.html)에 따르면 실험 경고 출력도 이 버전에서 제거됐습니다.
- **2025년 2월 — TypeScript 5.8**: [`--erasableSyntaxOnly`](https://devblogs.microsoft.com/typescript/announcing-typescript-5-8/) 옵션이 추가돼, 컴파일러 차원에서 "지울 수 있는 문법만 쓰는지"를 검증할 수 있게 됐습니다.

정리하면 2025년 8월 현재, 최신 Node에서는 별도 설정 없이 `node app.ts`가 동작합니다. 제가 쓰는 대부분의 머신에서도 이제 이것이 기본 실행 방식입니다.

## 핵심 개념: 타입 제거는 무엇이고 무엇이 아닌가

### 타입 검사를 하지 않는다

가장 흔한 오해가 여기 있습니다. Node의 타입 제거는 **검사가 아니라 제거**입니다. [Node 공식 문서](https://nodejs.org/api/typescript.html)가 설명하듯 이 모드에서는 런타임 의미가 없는 TypeScript 전용 구문만 지원되며, 타입이 틀렸는지는 전혀 확인하지 않습니다. 타입 검사는 여전히 tsc의 몫이므로, CI에서 `tsc --noEmit`을 돌리는 단계는 그대로 두어야 합니다. 실행 편의성과 정적 검증을 분리해 생각해야 합니다.

### 트랜스파일이 아니다

enum을 객체로 바꾸거나 최신 문법을 하위 버전으로 낮추는 변환(transform)은 하지 않습니다. 순수하게 타입 관련 구문만 지웁니다. 그래서 대상 문법이 제한되고, 이것이 다음 절의 제약으로 이어집니다.

### 제약: enum, namespace, parameter properties

Node 22.6 릴리스 노트는 초기 제약으로 "인라인 타입 주석만 지원하고 enum이나 namespace 같은 기능은 지원하지 않는다", "import/require에 파일 확장자를 명시해야 한다", "타입 임포트에 type 키워드를 강제한다", "node_modules 내부의 TypeScript는 기본 비활성"을 명시했습니다. TypeScript 5.8 문서도 같은 맥락을 설명합니다. 런타임 코드를 생성하는 문법은 "지울 수 없는 문법"이기 때문입니다.

```ts
// 지울 수 있는 문법 — 타입 제거로 실행 가능
type Status = "idle" | "loading" | "done";
const double = (n: number): number => n * 2;

// 지울 수 없는 문법 — 에러 발생
enum Role {
  Admin,
  User,
}

namespace Config {
  export const timeout = 3_000;
}

class Order {
  constructor(public id: string) {}
}
```

- **enum**: 런타임 객체를 만들므로 지울 수 없습니다.
- **namespace(값을 담는 경우)**: IIFE로 변환되는 코드 생성 문법입니다.
- **parameter properties**: 생성자 파라미터의 `public`/`private` 수식어는 필드 할당 코드로 확장돼야 합니다.

## 실전: .ts 그대로 실행해 보기
먼저 구조를 바꿔야 할 것들입니다. enum은 유니언 타입과 `as const` 배열로, parameter properties는 명시적 필드 할당으로 마이그레이션합니다.

```ts
// Before — 런타임 객체를 생성하는 enum
enum Role {
  Admin = "admin",
  User = "user",
}

// After — 지울 수 있는 리터럴 유니언
type Role = "admin" | "user";
const roles = ["admin", "user"] as const;

function canManage(role: Role): boolean {
  return role === "admin";
}
```

```ts
// Before — parameter properties
class Invoice {
  constructor(
    public id: string,
    private amount: number,
  ) {}
}

// After — 명시적 필드 할당
class Invoice {
  public id: string;
  private amount: number;

  constructor(id: string, amount: number) {
    this.id = id;
    this.amount = amount;
  }
}
```

실행은 플래그 없이 끝납니다.

```bash
# Node 23.6+, 또는 22.18+ LTS — 바로 실행
node src/server.ts

# Node 22.6 ~ 22.17 시절에는 실험 플래그가 필요했습니다
node --experimental-strip-types src/server.ts
```

마지막으로 tsconfig에 한 줄을 추가해 실수를 컴파일 타임에 잡습니다. [TypeScript 5.8의 `erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/erasableSyntaxOnly.html)는 지울 수 없는 문법을 쓰면 컴파일 에러로 알려줍니다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "strict": true,
    "erasableSyntaxOnly": true
  }
}
```

이 조합("Node 타입 제거 + tsc 검사")으로 실행 손실 없이 정적 타입 안전을 유지할 수 있습니다. import 시 `.js` 확장자가 아니라 `.ts` 확장자를 쓰게 되는 점 등 세부 규칙이 있어 처음 몇 번은 에러를 만나겠지만, 메시지가 친절해서 금방 익숙해집니다.

## tsx, Bun, Deno와의 비교

타입 제거는 Node만의 시도가 아닙니다. 오히려 다른 런타임들이 먼저 보여준 UX를 Node가 따라온 셈입니다.

- **tsx**: [tsx](https://github.com/privatenumber/tsx)는 Node 위에서 TypeScript를 즉시 실행하게 해 주는 도구로, 설정 없이 쓸 수 있어 이미 사실상 표준이 된 선택지입니다. Node 내장 타입 제거가 보급된 지금도 감시 재시작(watch), 실행기 통합 같은 개발 경험 때문에 여전히 유용합니다.
- **Bun**: TypeScript를 [네이티브로 실행](https://bun.com/docs/runtime/typescript)하는 런타임입니다. 실행 속도와 패키지 관리 통합이 강점이고, 별도 변환 설정이 필요 없다는 점에서 방향성이 Node의 타입 제거와 같습니다.
- **Deno**: TypeScript가 [퍼스트클래스 언어](https://docs.deno.com/runtime/fundamentals/typescript/)인 런타임으로, 설정 없이 `.ts`를 실행해 왔습니다. Node가 이 모델의 유용성을 확인하고 도입한 선례로 볼 수 있습니다.

차이를 요약하면 이렇습니다. Node 내장 기능은 "설정 없는 표준 경로", tsx는 "개발 서버·스크립트용 편의 계층", Bun/Deno는 "처음부터 TS를 전제로 설계한 대안 런타임"입니다. 상황에 따라 섞어 쓰는 것이 이상하지 않고, 실제로 그렇게 쓰고 있습니다.

## ts-node에서 tsx로 마이그레이션

기존 프로젝트가 ts-node에 묶여 있다면, Node 내장 실행으로 바로 넘어가기 전에 중간 단계로 tsx 이관을 권합니다. ts-node는 오랜 표준이었지만 ESM 조합의 설정 민감성으로 유명했고, 새로 시작하는 프로젝트에서 선택할 이유가 줄어든 것도 사실입니다. 이관은 package.json의 스크립트 교체가 대부분입니다.

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "typecheck": "tsc --noEmit",
    "start": "node src/server.ts"
  }
}
```

변경 포인트는 세 가지입니다.

1. `ts-node`, `ts-node-dev` 의존성 제거 후 `tsx` 추가.
2. `NODE_OPTIONS="--require ts-node/register"` 같은 환경 변수 조합 삭제.
3. 타입 검사를 `tsc --noEmit` 스크립트로 분리해 CI에 유지.

이렇게 하면 로컬에서는 tsx의 watch, 배포 환경에서는 Node 내장 타입 제거(`node src/server.ts`)라는 조합이 자연스럽게 완성됩니다. 운영 배포는 프로젝트 설정에 맞춰 검증한 뒤 단계적으로 전환하는 것을 권합니다.

## 마무리

타입 제거 시대의 TypeScript는 "컴파일 언어가 아니라, 타입 검사기가 달린 JavaScript"로 정체가 정리되어 가는 느낌입니다. 실행은 Node가, 검사는 tsc가 담당하고, 그 경계를 `erasableSyntaxOnly`가 지켜 줍니다. 남는 비용은 enum·namespace 같은 레거시 문법의 점진적 정리뿐입니다. 빌드 단계 하나가 사라지는 것이 주는 개발 경험의 개선은 생각보다 크니, 아직이라면 이번 주말에 작은 스크립트부터 옮겨 보시길 권합니다.

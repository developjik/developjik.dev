# 로컬 퍼스트 웹 앱: 오프라인에서도 동작하는 소프트웨어

## 개요

출퇴근길 지하철에서 메모 앱이 로딩 화면에 멈춰 있는 경험을 하고 나서 "왜 내 메모는 내 기기에 없을까"라는 의문이 시작이었습니다. 로컬 퍼스트(local-first) 소프트웨어는 데이터와 연산의 주체를 서버가 아니라 사용자 기기에 두는 아키텍처입니다. 네트워크 상태와 무관하게 즉시 반응하고, 나중에 동기화합니다. 이 글에서는 로컬 퍼스트 앱을 만들 때 마주치는 개념들 — CRDT, 동기화 전략, 낙관적 UI — 을 정리합니다.

## 왜 어려운가: 충돌의 문제

겉보기에는 "데이터를 로컬 저장소에 넣고 나중에 서버로 보내면 끝" 같지만, 진짜 문제는 여러 기기를 쓰는 순간 시작됩니다. 지하철에서 휴대폰으로 수정한 내용과 집에서 노트북으로 수정한 내용이 만나면 누가 이기나요? 마지막 쓰기 승리(last-write-wins)로 처리하면 어느 한쪽의 수정이 조용히 사라집니다. 이 충돌 문제가 로컬 퍼스트 설계의 중심 과제입니다.

## CRDT: 자동으로 합쳐지는 데이터

CRDT(Conflict-free Replicated Data Type, 무충돌 복제 데이터 타입)는 이 문제에 대한 대표적인 답입니다. 핵심 아이디어는 간단합니다. "어떤 순서로, 어떤 기기에서 병합해도 항상 같은 결과로 수렴하는 데이터 구조"를 만드는 것입니다.

가장 이해하기 쉬운 예는 증가하는 카운터(G-Counter)입니다. 각 기기가 자기 슬롯만 증가시키고, 병합은 슬롯별 최댓값을 취합니다.

```ts
type GCounter = Record<string, number>; // key: 기기 ID

function increment(counter: GCounter, deviceId: string): GCounter {
  return { ...counter, [deviceId]: (counter[deviceId] ?? 0) + 1 };
}

function merge(a: GCounter, b: GCounter): GCounter {
  const merged = { ...a };
  for (const [id, count] of Object.entries(b)) {
    merged[id] = Math.max(merged[id] ?? 0, count);
  }
  return merged;
}

function value(counter: GCounter): number {
  return Object.values(counter).reduce((sum, n) => sum + n, 0);
}
```

어느 기기에서 먼저 merge해도 결과가 같다는 성질(교환·결합·멱등) 덕분에 중앙 조정자 없이 충돌이 없습니다. 텍스트 편집처럼 순서가 중요한 데이터는 리스트 CRDT(예: Yjs, Automerge가 제공하는 구현)를 쓰는데, 원리는 같습니다. 삽입·삭제에 고유 식별자를 붙여서 양쪽 변경을 모두 보존하며 합칩니다. 직접 구현하기보다는 성숙한 라이브러리를 쓰는 것이 정신건강에 이롭습니다.

## 동기화 전략: 언제, 무엇을, 어떻게

CRDT가 "합치는 방법"이라면 동기화 전략은 "언제 무엇을 주고받을지"입니다. 제가 지키는 설계 원칙은 세 가지입니다.

- **변경 단위는 오퍼레이션**: 문서 전체가 아니라 변경 사항(업데이트 벡터와 함께)을 주고받아야 모바일 데이터가 살아남습니다.
- **푸시와 폴의 병용**: 온라인일 때는 WebSocket 같은 실시간 채널로, 재접속 시는 오랜 변경분을 일괄 폴링으로 받습니다.
- **영구 저장소가 동기화의 진실 원천**: 브라우스 메모리가 아니라 IndexedDB(또는 SQLite/WASM)에 상태와 함께 보관해야 새로고침에도 살아남습니다.

동기화 코드의 뼈대는 대략 이렇습니다.

```ts
async function sync(doc: Y.Doc, socket: WebSocket) {
  const state = Y.encodeStateVector(doc);       // 내가 가지고 있는 변경까지의 요약
  socket.send(state);
  socket.onmessage = async (event) => {
    const update = new Uint8Array(await event.data.arrayBuffer());
    Y.applyUpdate(doc, update);                  // CRDT 병합 - 충돌 걱정 없음
  };
}
```

서버는 클라이언트 간 업데이트를 중계하는 역할만 하면 되고, 권한·과금 같은 도메인 로직은 서버가 검증하는 계층을 따로 둡니다.

## 낙관적 UI: 로컬이 먼저다

로컬 퍼스트 앱의 사용자 경험은 낙관적 업데이트(optimistic update)로 완성됩니다. 서버 응답을 기다리지 않고 로컬 변경을 즉시 반영하고, 동기화는 뒤에서 조용히 일어나게 하는 것입니다. 이때 상태 표시가 중요합니다. 저는 동기화 상태를 "동기화됨 / 동기화 중 / 동기화 실패(재시도)" 세 가지로 명시적으로 보여줍니다. 실패를 숨기면 사용자는 다른 기기에서 변경이 사라졌을 때 앱을 의심하게 됩니다.

로컬 퍼스트에서 낙관적 업데이트는 선택이 아니라 기본값입니다. 어차피 병합이 안전하니 "일단 적용하고 나중에 합친다"는 순서가 자연스럽기 때문입니다.

## 트레이드오프: 공짜가 아니다

장점만 있는 건 아닙니다. 모든 데이터를 기기에 두면 삭제·이관 정책이 복잡해지고, 스키마 마이그레이션을 여러 버전의 클라이언트와 함께 다뤄야 합니다. CRDT 구조는 일반 RDB보다 질의가 어렵고 저장 용량도 더 씁니다. 협업·권한 검사가 중심인 도구라면 서버 권위 모델이 여전히 단순할 수 있습니다. 로컬 퍼스트는 "네트워크와 무관한 반응성"이 핵심 가치일 때 택하는 아키텍처지 만능 해법이 아닙니다.

## 마무리

로컬 퍼스트는 데이터의 소유권을 사용자에게 돌려주고, 네트워크를 필수 조건이 아니라 개선 사항으로 격하시키는 설계 관점입니다. 기술적으로는 CRDT로 충돌 없는 병합을 만들고, 오퍼레이션 기반 동기화를 설계하고, 낙관적 UI로 즉각성을 주는 삼단 구성입니다. 다음에 오프라인에서 죽는 앱을 만나게 되면, 문제는 네트워크가 아니라 아키텍처라는 관점에서 한 번 살펴보시길 권합니다.

# AI 페어 프로그래밍: 사고방식의 전환

## 개요

2025년까지는 "AI에게 코드를 생성하게 한다"가 주된 사용법이었다면, 2026년의 저에게 AI 페어 프로그래밍은 "AI가 쓴 코드를 내가 빠르게 검증한다"로 바뀌었습니다. 도구가 아니라 사고방식이 바뀐 경험을 정리해봅니다.

## 생성에서 검증으로

초기에는 프롬프트를 다듬는 데 시간을 쏟았습니다. 지금은 그 시간의 상당 부분이 검증으로 이동했습니다. AI가 1분 만에 만들어주는 코드를 제대로 판단하려면, 저는 다음을 확인합니다.

- 요구사항의 경계 케이스를 코드가 실제로 처리하는가
- 의존성을 과하게 끌어오지 않았는가
- 기존 코드 컨벤션과 일치하는가
"잘 부탁해"식 프롬프트보다 중요해진 것은 컨텍스트입니다.
생성 속도가 빨라질수록 병목은 검증 능력이 됩니다. 그래서 리뷰 스킬이 곧 생산성이 되는 시대라고 느낍니다.

## 프롬프트가 아니라 컨텍스트 설계

"잘 부탁해"하는 프롬프트보다 중요해진 것은 컨텍스트입니다. 프로젝트 루트에 규칙 파일을 두는 것만으로 응답 품질이 달라졌습니다.

```markdown
# docs/ai-guidelines.md

- 컴포넌트는 함수형으로 작성한다
- 상태 관리는 zustand를 사용한다
- 테스트는 vitest + testing-library 조합을 유지한다
- any 사용 금지, unknown + 타입 가드로 처리한다
```

이런 파일 하나가 매번 프롬프트에 붙이던 지시를 대신합니다. 컨텍스트 설계는 한 번 해두면 계속 복리로 작동하는 투자입니다.

## 내 워크플로 변화

실제로 제 워크플로가 이렇게 바뀌었습니다.

```text
이전: 요구사항 → 직접 설계 → 직접 구현 → 셀프 리뷰
이후: 요구사항 → 컨텍스트 준비 → AI 초안 생성 → 검증·수정 → 테스트로 확정
```

특히 테스트 코드는 AI에게 먼저 쓰게 하고, 구현이 그 테스트를 통과하는지 보는 흐름을 자주 씁니다.

```typescript
import { describe, it, expect } from 'vitest';
import { formatKrPrice } from './format';

describe('formatKrPrice', () => {
  it('천 단위 콤마와 원화 기호를 붙인다', () => {
    expect(formatKrPrice(1234567)).toBe('₩1,234,567');
  });

  it('0원과 음수도 처리한다', () => {
    expect(formatKrPrice(0)).toBe('₩0');
    expect(formatKrPrice(-5000)).toBe('-₩5,000');
  });
});
```

테스트를 명세로 먼저 확정하니 AI의 구현이 아무리 바뀌어도 받아들일 기준이 명확해집니다.

## 여전히 제가 하는 일

아키텍처 결정, 도메인 모델링, 팀과의 트레이드오프 논의는 여전히 제 몫입니다. AI는 넓은 지식은 갖고 있지만, 우리 팀의 역사와 제약을 알지 못합니다. "무엇을 AI에게 맡길지"를 정하는 것 자체가 엔지니어의 판단 영역이 되었습니다.

## 마무리

AI 페어 프로그래밍의 본질은 타이핑 절약이 아니라, 엔지니어의 역할을 생성에서 검증과 설계로 옮기는 것이라고 생각합니다. 컨텍스트를 설계하고, 검증 기준을 세워두면 AI는 꽤 믿을 만한 페어가 됩니다.

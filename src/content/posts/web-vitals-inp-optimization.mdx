# INP 최적화 실전: 느린 상호작용 잡기

## 개요

Core Web Vitals에서 FID가 제외되고 INP(Interaction to Next Paint)가 대신 들어온 뒤로, "클릭했는데 반응이 없는" 문제가 지표로 직접 잡히게 됐습니다. 실제 프로젝트에서 목록 필터 버튼이 느리다는 신고를 받고 INP를 잡았던 과정을 정리합니다.

## INP란 무엇인가

INP는 페이지 로드 전체 구간에서 사용자 상호작용(클릭, 키 입력, 탭)부터 다음 페인트까지의 지연을 샘플링하고, 그중 가장 나쁜 값에 가깝게 계산하는 지표입니다. FID가 "첫 상호작용의 입력 지연"만 봤다면, INP는 페이지 생애 전체의 모든 상호작용을 봅니다. 그래서 첫 로딩은 빠른데 특정 버튼이 무거운 페이지에서 INP가 나쁘게 나옵니다.

Chrome의 기준은 대략 이렇습니다. 좋음 200ms 이하, 개선 필요 200~500ms, 나쁨 500ms 초과. 개발자 도구의 Performance 패널에서 상호작용을 기록하면 각 인터랙션의 input delay / processing duration / presentation delay로 분해해서 볼 수 있어, 병목이 어디인지 먼저 진단하는 습관이 중요합니다.

## 롱태스크가 주범이다

INP를 나쁘게 만드는 전형적인 원인은 메인 스레드를 오래 점유하는 롱태스크(50ms 초과)입니다. 필터 버튼 클릭 핸들러에서 수천 개 아이템을 정렬·필터링하면서 리렌더까지 한 번에 하면, 하나의 태스크가 수백 ms를 잡아먹습니다. 메인 스레드가 점유된 동안에는 페인트도 입력 처리도 밀립니다.

첫 번째 처방은 태스크를 잘게 쪼개는 것입니다. 큰 배열 처리를 청크로 나누고, 각 청크 사이에 브라우저에게 제어를 돌려주면 페인트와 다른 입력이 끼어들 수 있습니다.

## scheduler.yield로 제어 돌려주기

전통적으로는 `setTimeout(task, 0)`으로 양보하는 패턴을 썼는데, 이건 브라우저 우선순위 큐 뒤쪽으로 밀려나 오히려 지연이 커질 수 있습니다. 이제 Chrome에서는 `scheduler.yield()`가 안정적으로 제공되고 있어, "지금 태스크를 끊되 가능한 한 앞쪽에서 이어서 실행"할 수 있습니다.

```typescript
async function processInChunks<T>(
  items: T[],
  chunkSize: number,
  handle: (chunk: T[]) => void,
): Promise<void> {
  const scheduler = window.scheduler as
    | { yield?: () => Promise<void> }
    | undefined;

  for (let i = 0; i < items.length; i += chunkSize) {
    handle(items.slice(i, i + chunkSize));
    if (scheduler?.yield) {
      await scheduler.yield();
    } else {
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
  }
}

// 사용 예: 필터 결과를 청크 단위로 반영
await processInChunks(products, 500, (chunk) => {
  visibleItems.push(...chunk.filter(matchesFilter));
});
```

지원하지 않는 브라우저를 위해 `setTimeout` 폴백을 남겨두는 방식이 무난합니다. 폴백이 없는 환경에서도 동작은 하니 점진적 향상으로 보면 됩니다.

## React에서는 useTransition

React 앱이라면 상태 업데이트 자체를 낮은 우선순위로 표시하는 `useTransition`이 정석에 가깝습니다. 무거운 갱신을 트랜지션으로 감싸면 React는 급한 작업(페인트, 다른 입력)을 먼저 처리하고 여유 있을 때 갱신합니다.

```tsx
import { useMemo, useState, useTransition } from 'react';

export function ProductList({ products }: { products: Product[] }) {
  const [query, setQuery] = useState('');
  const [deferredQuery, setDeferredQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  const filtered = useMemo(
    () =>
      deferredQuery === ''
        ? products
        : products.filter((p) => p.name.includes(deferredQuery)),
    [products, deferredQuery],
  );

  return (
    <div>
      <input
        value={query}
        onChange={(e) => {
          setQuery(e.target.value);
          startTransition(() => {
            setDeferredQuery(e.target.value);
          });
        }}
      />
      {isPending ? <p>갱신 중…</p> : null}
      <ul>
        {filtered.map((p) => (
          <li key={p.id}>{p.name}</li>
        ))}
      </ul>
    </div>
  );
}
```

입력 자체는 동기 상태(`query`)로 즉시 반영하고, 무거운 목록 갱신은 트랜지션 상태(`deferredQuery`)로 미루는 구조입니다. `isPending`으로 로딩 표시를 줄 수 있어 사용자에게 "반응이 있다"는 피드백도 남습니다. 검색 입력에서 체감 지연이 크게 줄어드는 대표적인 패턴입니다.

## 측정하고 다시 확인하기

최적화는 측정 없이 끝내면 안 됩니다. 실사용자 데이터는 `web-vitals` 라이브러리로 수집합니다.

```typescript
import { onINP } from 'web-vitals';

onINP((metric) => {
  navigator.sendBeacon(
    '/vitals',
    JSON.stringify({
      name: metric.name,
      value: metric.value,
      rating: metric.rating,
      entries: metric.entries.map((e) => ({
        interactionTarget: e.interactionTarget,
        duration: e.duration,
      })),
    }),
  );
});
```

어떤 요소가 나쁜 INP를 만드는지 `interactionTarget`으로 잡을 수 있어서, 실사용자 환경의 병목 지점을 찾기 좋습니다. 제 경우 특정 필터 버튼 하나가 전체 INP를 끌어내리고 있었는데, 이 데이터 덕분에 빠르게 특정할 수 있었습니다.

## 마무리

INP 개선의 핵심을 정리하면, 1) Performance 패널과 실사용자 데이터로 병목 상호작용을 특정하고, 2) 긴 태스크를 잘게 쪼개 `scheduler.yield()`로 양보하며, 3) React라면 `useTransition`으로 우선순위를 분리하는 것입니다. 화면 밖에서 벌어지던 "느림"이 이제 지표로 보이기 때문에, 사용자 경험 개선의 우선순위를 세우기도 훨씬 쉬어졌습니다.

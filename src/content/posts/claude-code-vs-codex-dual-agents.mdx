# Claude Code vs Codex — 둘 다 쓰는 사람의 실전 비교 (2026년 말)

"Claude Code 써봤어?" / "Codex가 더 나던데." — 어느 쪽이냐는 질문은 이제 그만 답하겠다. **나는 둘 다 매일 쓴다.** 한쪽만 쓰는 사람의 리뷰는 결국 그 도구의 세계관에 갇혀 있고, 두 도구를 같은 코드베이스에 돌리면 각자의 성격이 선명하게 드러난다.

이 글은 몇 달간 Claude Code와 Codex를 병행하며 얻은 실전 비교다. 결론부터: **확장성은 Claude Code, 묵직한 한 방은 Codex. 그래서 나는 구현과 리뷰를 분리해서 쓴다.**

## 비교 전에: 대상 버전과 내 사용 맥락

- **Claude Code 2.x** — hooks, skills, sub-agents, plugins 생태계가 갖춰진 상태
- **Codex** — CLI 기반, 설정이 얇고 예측 가능하며 컨텍스트 처리가 보수적
- 내 맥락: 프론트엔드(TypeScript/React/Astro) + Rust 사이드 프로젝트, 두 에이전트를 하나의 데몬으로 묶어 세션/권한/히스토리를 통합 관리

## 1. 확장성 — Claude Code가 압도적

Claude Code는 확장 지점이 명확하다.

| 확장점 | 위치 | 쓰는 순간 |
| --- | --- | --- |
| 커스텀 명령 | `.claude/commands/` | 반복 프롬프트의 명령화 (`/handoff` 등) |
| Skills | `SKILL.md` 폴더 | 온디맨드 도메인 지식 (컨텍스트 절약) |
| Hooks | `settings.json` | 응답 종료 후 알림, "계속해라" 자동 주입 |
| Sub-agents | `.claude/agents/` | 탐색 전용 에이전트 분리, 모델 지정 |
| Plugins | 위의 것들을 묶는 배포 단위 | 팀/저장소 단위 워크플로 자산화 |

특히 sub-agents는 강력하다. 읽기 전용 Explore 에이전트를 가변 모델로 돌려 코드베이스 조사를 맡기고, 메인 컨텍스트는 설계에 아끼는 패턴이 가능하다.

**Codex는 이런 확장 계층이 의도적으로 얇다.** hooks도 sub-agents도 없다. 대신 그 복잡성을 통째로 안아야 한다는 부담이 없다. "설정이 없다"는 건 "관리할 것이 없다"는 뜻이기도 하다.

## 2. 일관성 — Codex의 미덕

Codex로 돌리면 이상하리만치 **결과의 편차가 작다.** 같은 프롬프트를 열 번 돌려도 아홉 번은 비슷한 품질이 나온다. 컨텍스트를 보수적으로 쓰는 성향 탓에, 긴 세션 후반에 갑자기 엉뚱한 방향으로 새는 일이 드물다.

Claude Code는 확장 생태계의 대가를 치른다. hooks와 skills와 sub-agents가 얽히면 **내가 만든 워크플로가 복잡해질수록 실패 지점도 늘어난다.** Stop 훅이 잘못 걸리면 무한 루프 돌리고, 스킬이 꼬이면 컨텍스트 예산이 새는데 원인 파악이 한참 걸린다.

## 3. 실전 배치 — 역할 분리가 답이다

내 운용 원칙은 단순하다.

1. **구현 = Claude Code.** 스킬로 프로젝트 관례를 학습시켜 두면, 세팅 비용을 넘는 생산성이 나온다.
2. **리뷰/검증 = Codex.** 코드를 쓴 에이전트는 자기 코드를 못 본다. 성격이 다른 에이전트의 눈이 낫다. 편차가 작은 만큼 리뷰 품질이 안정적이다.
3. **의견 충돌 = 사람의 신호.** 둘이 다른 방향을 제시하면, 그곳이 진짜 설계 결정이 필요한 곳이다.

이 구조의 전제는 세션 관리다. 두 에이전트의 히스토리가 각자 흩어지면 "지난번에 뭐라고 리뷰받았더라"가 무너진다. 그래서 나는 세션을 통합하는 층을 직접 쓰고 있다 — 이 부분은 [나의 LLM 코딩 워크플로](/posts/my-llm-coding-workflow-2026)에서 자세히 다뤘다.

## 4. 코스트 감각

- Claude Code는 컨텍스트를 적극적으로 쓴다. 빠르고 똑똑하지만 **토큰이 잘 새는 구조**라, 긴 세션에서는 compaction 타이밍(컨텍스트 60%쯤)을 내가 관리해야 한다.
- Codex는 보수적이라 **같은 작업에 토큰이 덜 드는 편**이지만, 큰 산출물을 한 번에 뽑는 순간의 화력은 아쉬울 때가 있다.

즉 "비싼 만큼 화력" vs "싸고 안정"의 관계가 성립한다. 그래서 크레이트 전체를 다루는 설계는 Claude, PR 단위 검증은 Codex로 나간다.

## 어떤 사람에게 무엇을 권하나

- **처음 에이전트를 도입하는 팀** → Codex 먼저. 설정이 없어서 도입 회의가 짧고, 결과가 일정해서 신뢰가 쌓인다.
- **혼자 여러 저장소를 굴리는 사람** → Claude Code. 스킬/명령을 저장소마다 자산화하면 스케일이 된다.
- **검증 중심의 시니어 역할** → 둘 다. 교차 리뷰 구조 자체가 품질 장치가 된다. [PR 리뷰 에이전트 가드레일 설계법](/posts/frontend-ai-pr-review-agent-guardrails)과 함께 보면 좋다.

마지막에 정답을 하나만 고르는 건 이 시대의 습관이 아니다. 도구는 바뀌어도 — 내 워크플로 자산(스킬, 명령, 세션 히스토리)은 남는다. 그 자산을 어느 쪽에 쌓을 것인가가 진짜 질문이다.

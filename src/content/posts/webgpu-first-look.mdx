# WebGPU 첫인상: WebGL의 다음

## 개요

개인 프로젝트에 데이터 시각화를 붙이면서 수십만 점을 그려야 할 일이 있었는데, WebGL로 파이프라인을 짜는 건 늘 진입 장벽이 높았습니다. 그때 주요 브라우저가 모두 WebGPU를 지원하게 됐다는 소식을 접하고 학습 겸사 겸사 살펴봤습니다. 첫인상을 한 줄로 요약하면 "브라우저 API인데 그래픽 API다"였습니다. 이 글은 WebGPU가 왜 존재하고 무엇이 달라지는지, 프론트엔드 개발자 관점에서 정리한 기록입니다.

## 왜 WebGL을 대체하려는가

WebGL은 2011년에 나온 OpenGL ES 2.0/3.0의 브라우저 바인딩입니다. 당시 기준으로는 훌륭했지만 15년이 지나며 한계가 뚜렷해졌습니다.

- 설계 자체가 2000년대 GPU 아키텍처 기반이라 현대 GPU의 기능을 노출하지 못합니다.
- 상태 관리가 전역 상태 기반이라 무엇이 현재 상태인지 추적하기 어렵고 버그의 온상이 됩니다.
- 무엇보다 **범용 컴퓨트(연산) 기능이 없습니다.** GPU 병렬 연산을 하려면 픽셀 셰이더를 우회해서 쓰는 꼼수를 써야 했습니다.

WebGPU는 이 세 가지를 해결합니다. Vulkan, Metal, Direct3D 12의 개념을 가져와 브라우저에 맞게 추상화했고, 자체 셰이더 언어인 WGSL(WebGPU Shading Language)을 사용합니다.

## 첫인상: API가 현대적이다

실제로 초기화 코드를 짜보면 가장 먼저 느끼는 건 WebGL과 달리 명시적이라는 점입니다. 상태를 암묵적으로 공유하지 않고 파이프라인 객체에 미리 굽습니다.

```js
const adapter = await navigator.gpu.requestAdapter();
const device = await adapter.requestDevice();

const format = navigator.gpu.getPreferredCanvasFormat();
const context = canvas.getContext("webgpu");
context.configure({ device, format });

const pipeline = device.createRenderPipeline({
  layout: "auto",
  vertex: {
    module: device.createShaderModule({ code: wgslShader }),
    entryPoint: "vs_main",
  },
  fragment: {
    module: device.createShaderModule({ code: wgslShader }),
    entryPoint: "fs_main",
    targets: [{ format }],
  },
  primitive: { topology: "triangle-list" },
});
```

`device`라는 개념이 중심에 있는 것, 파이프라인을 생성 시점에 확정하는 것, 오류가 콜백(`device.pushErrorScope` / `uncapturederror` 이벤트)으로 잡히는 것이 Vulkan 계열 API의 영향입니다. WebGL의 `gl.getError()`를 매번 호출하던 시절과 비교하면 디버깅 경험이 좋아졌습니다.

## 컴퓨트 셰이더: 가장 큰 변화

WebGPU의 핵심 업데이트는 컴퓨트 셰이더입니다. 그래픽 파이프라인(정점 → 래스터라이즈 → 픽셀)을 거치지 않고, GPU에 데이터 병렬 연산을 직접 맡길 수 있습니다. WGSL로 배열의 모든 요소를 두 배로 만드는 컴퓨트 셰이더는 이렇게 생겼습니다.

```wgsl
@group(0) @binding(0)
var<storage, read_write> data: array<f32>;

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) id: vec3u) {
  if (id.x >= arrayLength(&data)) { return; }
  data[id.x] = data[id.x] * 2.0;
}
```

호출하는 쪽에서는 버퍼를 만들어 바인딩하고 워크그룹 수를 지정해 디스패치합니다. `@workgroup_size(64)`는 한 워크그룹이 64개의 스레드를 처리한다는 뜻이고, JS 쪽에서 `Math.ceil(N / 64)`개의 워크그룹을 요청하면 배열 전체가 병렬로 처리됩니다. 이 패턴이 시각화에서 수십만 점의 위치 계산, 물리 시뮬레이션, 이미지 처리에 그대로 쓰입니다.

## 프론트엔드에서 가능해지는 것

컴퓨트가 브라우저에 들어온다는 건 그래픽 이외의 활로가 열린다는 뜻입니다.

- **고밀도 데이터 시각화**: 백만 점 산점도의 변환·필터링을 CPU가 아니라 GPU에서. 메인 스레드가 블로킹되지 않습니다.
- **이미지·영상 처리**: 실시간 필터, 리사이즈, 색 보정을 컴퓨트로.
- **온디바이스 ML 추론**: WebGPU 백엔드를 갖춘 추론 런타임(예: transformers.js, ONNX Runtime Web)이 WebGL 백엔드보다 빠른 추론을 보여주는 사례가 늘고 있습니다.
- 물론 폴백은 필요합니다. 다만 최근에는 폴백을 WebGL이 아니라 CPU(WASM/SIMD)로 두는 선택도 실용적입니다.

## 아직 불편한 것들

첫인상이 좋다고 전부 좋은 건 아닙니다. 학습 비용은 WebGL보다 확실히 높고, 개념(바인드 그룹, 파이프라인 레이아웃, 버퍼 매핑)이 많아서 "삼각형 하나 그리기"까지가 길었습니다. 대부분의 앱은 Three.js나 Babylon.js 같은 라이브러리를 통해서 쓰게 될 테고, 실제로 두 라이브러리 모두 WebGPU 백엔드를 제공하고 있으니 직접 다루는 것은 필요한 사람만 하면 됩니다. 그리고 규격 자체도 서브셋(subgroups 같은 확장)이 계속 논의 중이라 생태계가 안정기에 들어가는 중입니다.

## 마무리

WebGPU는 "더 빠른 WebGL"이 아니라 브라우저에 처음으로 제대로 된 GPU 연산 모델을 들여온 변화입니다. 당장 그래픽 작업이 없어도, 컴퓨트 셰이더라는 개념 하나는 미리 익혀두면 온디바이스 ML이나 고성능 시각화 요구가 왔을 때 선택지가 넓어집니다. 저는 삼각형 대신 배열 두 배 만들기부터 시작했는데, 그게 WebGPU를 이해하는 가장 빠른 길이었던 것 같습니다.

# 프론트엔드 보안 체크리스트: XSS부터 CSRF까지

## 개요

"보안은 백엔드 담당이 하는 거 아니에요?"라는 말을 몇 번 들었습니다. 실제로는 XSS는 프론트엔드 버그로 발생하고, CSRF 방어 쿠키 속성은 프론트와 백이 함께 정해야 하고, 서비스 워커의 오프라인 캐시는 프론트엔드 권한입니다. 이 글은 제가 프로젝트를 시작할 때마다 훑는 프론트엔드 보안 체크리스트를 정리한 것입니다.

## XSS: 위험한 HTML을 화면에 넣지 않기

XSS(Cross-Site Scripting)는 공격자가 삽입한 스크립트가 내 페이지에서 실행되는 공격입니다. 프론트엔드에서 가장 흔한 발생 경로는 사용자 입력을 HTML로 그대로 렌더링하는 것입니다.

React는 기본적으로 문자열을 이스케이프하기 때문에 아래는 안전합니다.

```tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>; // <script> 문자열도 텍스트로만 표시됨
}
```

문제는 이스케이프를 의도적으로 끄는 순간 생깁니다.

```tsx
// 위험: 사용자 입력을 HTML로 주입
function Comment({ html }: { html: string }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
```

`dangerouslySetInnerHTML`에 사용자 입력이 담기면 저장형 XSS가 됩니다. 부득이하게 써야 한다면 DOMPurify 같은 살균 라이브러리를 통과시킵니다.

```tsx
import DOMPurify from 'dompurify';

function RichText({ html }: { html: string }) {
  return (
    <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />
  );
}
```

URL도 검증 대상입니다. `javascript:` 스킴이 href에 들어가면 클릭 시 스크립트가 실행됩니다. 허용 프로토콜(http/https/상대 경로)만 통과시키는 유틸을 만들어 쓰고 있습니다.

## CSP: 실패해도 막아주는 두 번째 방어선

코드에서 조심하는 것은 첫 번째 방어선이고, Content-Security-Policy는 실수했을 때 피해를 줄이는 두 번째 방어선입니다. 응답 헤더로 인라인 스크립트와 외부 소스를 제한하는 정책입니다.

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  object-src 'none';
  frame-ancestors 'none';
  base-uri 'self'
```

이 정책만으로도 HTML 인젝션으로 `<script>`를 심어도 외부 스크립트 로드와 인라인 실행이 차단됩니다. 도입 팁은 두 가지였습니다.

- 처음부터 `Content-Security-Policy`로 강제하지 말고 `Content-Security-Policy-Report-Only`로 시작해 위반 리포트를 관찰합니다.
- 프레임워크가 인라인 스타일을 쓰는 경우가 많아 `style-src`는 `'unsafe-inline'`을 허용하더라도 `script-src`는 `'unsafe-inline'`을 절대 허용하지 않는 것이 원칙으로 삼았습니다.

## CSRF: SameSite와 토큰

CSRF(Cross-Site Request Forgery)는 사용자가 로그인한 상태에서 악성 사이트가 그 세션을 이용해 요청을 보내는 공격입니다. 프론트엔드 개발자가 알아야 할 방어의 핵심은 쿠키 속성입니다.

```
Set-Cookie: session=abc123;
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/
```

- `HttpOnly` — JS에서 쿠키를 읽지 못하게 해 XSS로 토큰이 유출되는 경로를 차단합니다.
- `Secure` — HTTPS에서만 전송됩니다.
- `SameSite=Lax` — 다른 사이트에서 온 요청에는 쿠키를 붙이지 않아 대부분의 CSRF를 막습니다.

`SameSite=Lax`가 기본값으로 자리 잡은 지금, 과거처럼 모든 요청에 CSRF 토큰을 붙이는 수고가 크게 줄었습니다. 다만 `SameSite=None`을 써야 하는 상황(서드파티 컨텍스트 쿠키)이라면 CSRF 토큰이나 `Origin` 검증 같은 다른 방어가 필요합니다. 백엔드와 이 속성 값을 반드시 함께 확인해야 하는 항목입니다.

## 서비스 워커의 양면성

서비스 워커는 강력한 만큼 공격 표면이기도 합니다. 워커가 한번 등록되면 이후 페이지 요청을 가로채서 제어할 수 있기 때문입니다. 제가 실수했던 장면과 지키는 규칙입니다.

```js
// 나쁜 예: 응답을 무조건 캐시에 담음
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('v1').then(async (cache) => {
      const response = await fetch(event.request);
      cache.put(event.request, response); // API 응답, 에러까지 담김
      return response;
    })
  );
});
```

이렇게 두면 로그인 응답이나 개인화된 API 응답이 캐시에 남아 다른 상황에서 재사용될 수 있습니다. 정리한 규칙은 다음과 같습니다.

- 인증이 필요한 API 요청은 캐시하지 않는다(또는 명시적인 네트워크 우선 정책만 쓴다).
- 캐시 이름에 버전을 붙이고(예: `static-v12`) activate 시 이전 캐시를 삭제한다.
- 캐시 전략은 경로별로 명시적으로 나열하고, "모든 요청 캐시" 같은 와일드카드는 쓰지 않는다.

서비스 워커 파일 자체는 HTTPS에서만 배포되므로 변조 위험은 낮지만, 워커가 오래 살아있는 특성상 배포 직후 `skipWaiting`과 `clients.claim()`의 동작을 정확히 이해하고 쓰는 것도 중요했습니다.

## 의존성 감사: npm audit과 lockfile

프론트엔드 번들은 의존성의 의존성까지 포함하기 때문에 공급망 공격에 노출되기 쉽습니다. 최소한으로 지키는 것들입니다.

```bash
npm audit --omit=dev
```

- CI에서 `npm audit`(프로덕션 의존성 기준)을 돌려 high 이상은 수정하도록 게이트를 걸었습니다.
- `package-lock.json`을 커밋하고, CI는 `npm ci`로 설치해 lockfile과의 불일치를 허용하지 않습니다.
- 브라우저 확장이 아니라 npm 패키지를 설치할 때는 다운로드 수·유지 상태·번들에 포함되는 의존성 수를 확인하는 습관을 들였습니다. 작은 유틸 패키지 하나가 수십 개의 전이 의존성을 끌고 오는 경우가 많았습니다.

## 마무리

체크리스트 전체를 요약하면 이렇습니다. (1) 사용자 입력은 이스케이프하고 `dangerouslySetInnerHTML`은 살균 후에만, (2) CSP를 Report-Only로 시작해 점진히 강화, (3) 쿠키는 HttpOnly·Secure·SameSite, (4) 서비스 워커는 경로별 명시적 캐시 전략, (5) CI에 의존성 감사와 lockfile 검증. 보안은 한 번의 점검이 아니라 배포 파이프라인에 박아둔 게이트로 유지되는 것이었다는 게 올해 가장 큰 교훈입니다. 새 프로젝트를 시작할 때 이 다섯 가지를 세팅하는 데는 반나절이면 충분했고, 그 반나절이 사고 이후의 며칠을 절약해 준다고 생각합니다.

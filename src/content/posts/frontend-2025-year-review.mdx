# 2025년 프론트엔드 회고: 내가 배운 것들

## 개요

올해는 기술적으로 가장 많이 바뀐 해였다고 생각합니다. 새 프레임워크를 여러 개 배운 해가 아니라, 테스트·성능·협업이라는 세 가지 축에서 일하는 방식이 바뀐 해였습니다. 연말을 맞아 무엇이 변했는지, 무엇이 아쉬웠는지, 내년에 뭘 하고 싶은지 정리해둡니다.

## 테스트: "테스트 없이는 리팩터링이 없다"

올해 초까지만 해도 저희 팀의 테스트는 손으로 클릭하는 QA가 전부였습니다. 작은 스타일 수정도 회귀가 터졌고, 리팩터링 제안이 나올 때마다 "건드리면 무너질 것 같은데"라는 말이 먼저 나왔습니다. 상황이 바뀐 계기는 유지보수 중인 장바구니 로직에서 같은 버그가 세 번째 재발한 사건이었습니다. 그때 "세 번 나면 테스트를 만든다"는 규칙을 세우고 시작했습니다.

처음에는 컴포넌트 테스트부터 만들려다 실패했습니다. 화면 전체를 테스트하려니 케이스가 폭발했습니다. 결국 정착한 구조는 이렇습니다.

- 순수 로직(가격 계산, 쿠폰 적용)은 Vitest 유닛 테스트로 최우선 커버
- 사용자 흐름(장바구니 담기 → 결제)은 Testing Library의 사용자 중심 쿼리로 몇 개만
- 핵심 E2E(로그인, 구매 완료)는 Playwright로 배포 환경에서

```ts
import { describe, it, expect } from 'vitest';
import { calculateTotal } from './cart';

describe('calculateTotal', () => {
  it('쿠폰 할인을 적용한 총액을 계산한다', () => {
    const items = [{ price: 30000, qty: 2 }, { price: 12000, qty: 1 }];
    expect(calculateTotal(items, { type: 'percent', value: 10 })).toBe(64800);
  });
});
```

테스트 코드 자체보다 큰 수확은 테스트를 위해 코드가 좋아졌다는 점이었습니다. 계산 로직을 컴포넌트에서 분리하고, DOM에 의존하던 상태를 순수 함수로 빼다 보니 자연스럽게 관심사가 나뉘었습니다. "테스트하기 어렵다"는 신호가 대부분 설계 문제였습니다.

## 성능: 숫자로 이야기하기

올해 성능 작업의 전환점은 "체감상 느리다"를 관측 가능한 지표로 바꾼 것이었습니다. web-vitals 라이브러리로 실사용자 지표(RUM)를 수집하고, Lighthouse CI로 성능 예산을 CI에 걸었습니다. 자세 내용은 앞서 쓴 글들에 정리했으니 여기서는 결과만 적습니다.

- LCP가 가장 자주 나빠졌고, 원인 대부분은 최적화 안 된 히어로 이미지였습니다. 적절한 크기의 responsive image와 `fetchpriority="high"`로 개선됐습니다.
- 번들이 큰 페이지의 공통점은 무거운 에디터/차트 라이브러리를 정적 import하는 것이었습니다. 코드 스플리팅(동적 import)만으로 초기 JS가 눈에 띄게 줄었습니다.
- 지표를 보여주고 나서 리뷰에서 "이 이미지 300KB인데 괜찮을까요?"라는 대화가 자연스럽게 생겼습니다. 도구가 문화를 바꾸는 것을 직접 봤던 해였습니다.

## 협업: 문서와 계약

올해 새로 배운 축은 협업입니다. 프론트와 백 사이에 API 응답 모양이 어긋나는 일이 잦아서, OpenAPI 스펙을 먼저 정의하고 모킹 서버로 프론트를 병렬 개발하는 흐름을 만들었습니다. 스펙이 코드 리뷰의 대상이 되면서 "되면 알려줄게"식 커뮤니케이션이 줄었습니다.

또 하나는 AI 도구를 페어로 삼는 습관입니다. 올해는 코드 작성보다 리뷰 준비와 레거시 파악에 AI를 쓰는 제 몫을 찾았습니다. 낯선 코드베이스의 구조를 정리해주고, 테스트 케이스 초안을 만들어주는 용도가 실무에 가장 잘 맞았습니다. 대신 결과는 반드시 직접 검증한다는 원칙을 지켰고, 이 원칙이 없었다면 생산성이 아니라 디버깅 시간이 늘었을 거라고 생각합니다.

## 잘한 것과 아쉬운 것

잘한 것.

- 테스트 규칙(세 번 재발하면 테스트)을 팀 규칙으로 만들고, 올해 스무 개 남짓한 회귀 방지 테스트를 쌓았습니다.
- 성능 지표 수집과 CI 예산 도입으로 성능 논의를 수준이 아니라 근거 중심으로 바꿨습니다.
- 접근성을 출시 기준에 넣었습니다. 키보드만으로 결제 흐름이 안 끝나던 문제를 발견하고 고친 것이 올해 가장 뿌듯한 수정이었습니다.

아쉬운 것.

- 타입 안전성 관리에 든 힘 대비 효과가 낮았습니다. `any`를 줄이는 데 몇 주를 쓰는 동안 정작 사용자에게 보이는 개선은 적었습니다. 다음엔 위험한 경로(결제, 인증)부터 좁게 잡을 것입니다.
- 문서화가 사람에 의존했습니다. 제가 쓴 문서가 제가 자리 비운 동안 방치되는 걸 여러 번 봤습니다. 문서에 "마지막 확인 날짜"를 강제하는 식의 썩는 속도 관리가 필요했습니다.
- 오픈소스로 내어놓은 것이 없습니다. 내부에서만 쓴 유틸이 몇 개 있는데 추릴 용기를 못 냈습니다.

## 2026년 목표

구체적으로 적어둡니다.

1. **테스트 커버리지의 질** — 커버리지 숫자보다 회귀 방지 횟수를 세는 습관. 분기마다 "이 테스트가 막아준 버그"를 기록해보려 합니다.
2. **성능 문화 확산** — 성능 예산을 다른 팀 설정으로 가져갈 수 있는 템플릿을 만들어 공유합니다.
3. **오픈소스 하나** — 올해 만든 유틸 중 하나는 추려서 공개합니다.
4. **AI 협업 원칙 문서화** — 검증 원칙과 쓰는 자리/안 쓰는 자리를 글로 남겨 팀의 기본값으로 만듭니다.

## 마무리

2025년을 한 문장으로 요약하면 "감이 아니라 근거로 일하는 방식을 배운 해"였습니다. 테스트는 근거가 되어주고, 성능 지표는 근거를 보여주고, 스펙은 협업의 근거가 되어주었습니다. 기술 목록은 계속 바뀌겠지만 이 방식은 오래 가져갈 수 있을 것 같습니다. 올해 도와주고 참아준 동료들에게 감사하고, 내년엔 이 정리를 다시 펴서 몇 개나 지켰는지 확인하러 오겠습니다.

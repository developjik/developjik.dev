# 증거 없는 자동화는 자동화가 아니다 — livesay · agent-ui-guard · proofshot으로 스트리밍 AI UI를 테스트하는 법

*1편의 세 번째 장면을 한 줄로 적어 두었다 — "스트리밍 채팅 UI는 DOM이 정상이고 클릭 테스트도 통과하는데 사용자만 막힌다." 이 글은 그 한 줄의 증거를 만드는 도구들에 대한 기록이다. 2026년 11월, livesay · streamscope · agent-ui-guard · proofshot · assignment-map의 코드와 측정값으로만 썼다.*

**시리즈** · 1편 [클라우드 서버 없이 브라우저가 로컬 Rust 데몬과 직접 대화하는 이유](/posts/local-first-ai-engineering) · 2편 [왜 코드·스펙 에이전트에서 임베딩과 벡터DB를 버렸는가](/posts/why-not-embeddings) · 3편 (이 글)

나는 자동화를 많이 만들었다. 수집 파이프라인이 매일 새벽에 돌고, 쇼츠가 정해진 시각에 올라가고, PR이 열리면 검사가 붙는다. 그런데 자동화를 만들수록 한 가지가 분명해졌다. **자동으로 도는 것과 증명되는 것은 다르다.** 파이프라인이 초록불인 채로 한 달 동안 틀린 데이터를 모을 수 있고, E2E 테스트가 전부 통과하는 채로 스크린리더 사용자가 채팅창을 쓸 수 없을 수 있다.

1편에서 세 번째 장면으로 적은 것이 정확히 그랬다. 토큰이 도착할 때마다 `aria-live` 영역을 다시 쓰는 채팅 UI. DOM은 정상이고, 클릭 스크립트 테스트는 통과하고, 로그에는 아무것도 없다. 사용자만 막힌다.

> **기존 UI 테스트가 이 화면에서 놓치는 네 가지**
>
> 1. **구간** — 40ms 동안 두 모달이 같이 떠 있었다. 스냅샷은 그 40ms를 보지 않는다.
> 2. **와이어** — 툴 인자 JSON이 절반만 도착한 프레임. 재현할 방법이 없으면 버그가 아니다.
> 3. **귀** — 라이브 리전 갱신 78회, 그중 7회만 발화. DOM 단언으로는 "시끄럽다"를 셀 수 없다.
> 4. **퇴화** — AI가 만든 화면이 조금씩 AI 티로 돌아가는 것. 픽셀도 DOM도 아니라 규칙 위반이다.

이 넷은 서로 다른 도구를 요구한다. 시간축 관측, 와이어 재현, 발화 계측, 전후 비교. 나는 그 넷을 각각 만들었고, 이름은 `agent-ui-guard`, `streamscope`, `livesay`, `proofshot`이다. 다섯 번째 `assignment-map`은 이 논리를 콘텐츠 파이프라인에 적용한 사례다.

## 1. 스냅샷은 순간이고, 버그는 구간이다

Playwright 어설션은 요청할 때 페이지를 샘플링한다. 이건 도구의 결함이 아니라 설계다. 대부분의 UI 버그는 지속되는 상태이기 때문이다. 버튼이 비활성인 채로 남아 있고, 에러 문구가 계속 떠 있고, 리스트가 비어 있다.

에이전트 UI는 다르다. 여기서 자주 나는 버그는 **지나가는 상태**다.

- 다이얼로그가 같은 프레임에 두 개 마운트되고, 다음 렌더에서 하나가 사라진다. 사용자는 그 한 프레임에 포커스를 잃었고, 앱은 "복구"됐다.
- 툴 호출 스피너가 자기 턴보다 오래 산다. 턴이 닫히고 나서 스피너만 남아 도는 상태가 200ms 존재하고, 그 뒤 리스트가 리렌더되며 사라진다.
- 끊긴 SSE가 `aria-busy`를 지우지 않는다. 그러면 입력창이 영원히 비활성이다. 이건 지속되는 버그인데, 원인이 스트림 중단이라는 **사건**이라 재현이 어렵다.

> **세 가지 시간 척도**
>
> - 프레임(16ms) — 두 모달이 동시에 보인 순간
> - 스트림(수 초) — 툴 인자가 반쯤 파싱된 채 도착하는 구간
> - 세션(수 분) — 응답이 끝났다는 사실을 아무도 말하지 않은 채 남는 침묵

기존 도구는 이 셋 중 어느 것도 자연스럽게 다루지 않는다. DevTools 네트워크 패널은 SSE 프레임을 보여주지만 재생하지 않는다. Playwright 트레이스는 DOM과 액션을 재생하지만 스트림 의미론이 없다. MSW는 HTTP를 목킹하지만 "스트림이 62% 지점에서 죽었다"를 표현할 수 없다. axe-core는 정적 스캔이라 발화 **횟수**를 세지 않는다.

그래서 도구를 만들 때 기준을 하나로 잡았다. **그 도구가 없으면 못 잡는 버그를 이름으로 말할 수 있어야 한다.** 아래 네 절은 각 도구가 잡는 버그의 이름과, 그 이름을 어떻게 종료 코드로 바꾸는지다.

## 2. livesay — 스크린리더에게 실제로 무슨 말이 갔는가

1편의 채팅 UI 장면을 실제로 재 보면 이렇다. 두 페이지가 있다. 같은 답변, 같은 속도, 같은 시뮬레이션 프로필(`nvda-like`). 하나는 토큰을 그대로 라이브 리전에 쓰고(`demo/bad.html`), 다른 하나는 내가 만든 안내자로 문장 단위로 말한다(`demo/good.html`).

| | 그냥 스트리밍 | `createStreamingAnnouncer` 적용 |
|---|---|---|
| 라이브 리전 갱신 | **78회** | 2회 |
| 초당 최대 갱신 | **36회** | 2회 |
| 발화 수 | 7회 | **4회** |
| 완료 알림 | **없음** | **있음** |
| 진단 결과 | 오류 3건 | 없음 |

표의 값은 저장소 README에 기록된 같은 데모의 측정값이다. CI는 정확한 값 대신 경계를 고정한다 — 발화는 2회 초과 10회 미만, 그리고 완료 문구가 실제로 발화되었는지.

두 번째 행을 보자. 초당 36회 갱신은 1초에 36번 다시 읽으라는 뜻이 아니다. **36번 중 대부분이 읽히지 않고 버려진다**는 뜻이다. 스크린리더는 말보다 느리다. 240ms에 한 단어를 읽는 프로필에서 이 답변은 19초가 넘고, 그 사이 수십 번의 갱신이 도착하면 앞의 발화는 계속 잘린다. 사용자가 듣는 것은 "A stre… Most chat inter… The result is a stut…"다.

### 2.1 프로브는 해석하지 않고 기록만 한다

계측기가 먼저 할 일은 판단을 미루는 것이다. `livesay`의 프로브는 앱 코드보다 먼저 페이지에 주입되어 두 가지만 기록한다. `ariaNotify()` 호출 전부와, 라이브 리전의 모든 변경이다.

```javascript
const wrappedNotify = function ariaNotify(message, opts) {
  const text = trimText(String(message ?? ''));
  const priority = opts?.priority === 'high' ? 'high' : 'normal';
  record({ type: 'notify', text, priority, impl: implementation === null ? 'none' : implIsPage ? 'page' : implAtInstall });
  if (implementation && text) {
    try { implementation.call(win, String(message ?? ''), opts); }
    catch { /* the page's own implementation must not break the audit */ }
  }
};

Object.defineProperty(win, 'ariaNotify', {
  configurable: true,
  enumerable: false,
  // Feature detection must stay honest: when the browser has no ariaNotify
  // and the page has not installed one, the property reads as undefined.
  // A probe that pretended otherwise would push apps onto a dead API.
  get: () => (implementation ? wrappedNotify : undefined),
  set: (value) => { /* 페이지가 나중에 넣는 폴리필도 가로챈다 */ },
});
```

getter가 `undefined`를 돌려주는 부분이 이 도구에서 가장 중요하다. 계측기가 "있는 척"하면 앱은 존재하지 않는 API에 코드를 쌓는다. 계측이 제품의 결정을 오염시키면 안 된다는 규칙 하나로, 기능 감지를 정직하게 유지했다.

기록은 **시각이 아니라 순번**으로 비교한다. `mark()`가 대기 중인 뮤테이션을 먼저 비우기 때문에 마크와 그 직전 변경이 같은 밀리초에 찍힐 수 있다. 타임스탬프로 정렬하면 순서가 뒤집힌다. 폭주하는 페이지를 막는 상한은 이벤트 60,000개다.

### 2.2 정답이 되는 스크린리더는 없다 — 그래서 프로필 세 개

여기서 갈등이 생긴다. "스크린리더가 무엇을 말할 것인가"에는 정답이 없다. NVDA와 VoiceOver와 Orca는 polite 갱신을 다르게 다룬다. 어떤 AT는 250ms 안의 갱신을 합치고, 어떤 AT는 전부 큐에 넣고, ARIA 스펙을 문자 그대로 읽는 구현은 atomic 리전을 처음부터 다시 읽는다.

그래서 도구는 하나의 정답을 고르지 않았다.

```javascript
export const PROFILES = {
  'nvda-like':    { msPerWord: 240, coalescePolite: true,  coalesceWindowMs: 250, notifyCoalesceMs: 250 },
  'voiceover-like': { msPerWord: 300, coalescePolite: false, coalesceWindowMs: 0, notifyCoalesceMs: 200 },
  'spec-strict':  { msPerWord: 240, coalescePolite: false, atomicReplacesPending: true, notifyCoalesceMs: 0 },
};
```

같은 녹음을 세 프로필로 다시 재생하면 결론이 갈린다. 망가진 페이지에서는 이렇게 갈린다.

| 프로필 | 발화 | 분당 단어 | 초당 갱신 | 판정 |
|---|---|---|---|---|
| `nvda-like` | 7 | 301 | 36 | FAIL |
| `voiceover-like` | 30 | 929 | 36 | FAIL |
| `spec-strict` | 31 | 956 | 36 | FAIL |

이 폭이 이 도구의 논지다. **한 AT에서 "괜찮아 보이는" 페이지가 다른 AT에서는 못 들을 것이 된다.** 그래서 리포트에는 항상 `simulated`라고 적는다. 실제 NVDA 녹음이 아니라는 사실을 숨기면, 이 도구는 정확성의 주장을 하게 되고 그 주장은 거짓이다.

### 2.3 규칙 여섯 개는 WCAG 판정이 아니라 발화 계약이다

| 규칙 | 심각도 | 조건 |
|---|---|---|
| `token-storm` | error | 라이브 리전(또는 `ariaNotify`)이 1초에 5회 이상 갱신 |
| `silent-completion` | error | 스트림이 끝났는데 아무 알림도 없음 |
| `silent-abort` | error | 중단·실패했는데 페이지가 조용함 |
| `assertive-abuse` | error | 답변당 assertive 알림 2회 이상 |
| `duplicate-announcement` | warn | 같은 문장이 8초 창 안에서 두 번 발화 |
| `partial-announcement` | warn | 앞 발화가 다음 발화의 잘린 접두사 |

임계값은 `DEFAULT_RULE_OPTIONS`에 그대로 적혀 있다. `stormWindowMs: 1000`, `stormMinUpdates: 5`, `assertiveLimit: 1`, `duplicateWindowMs: 8000`. 이 숫자들은 내가 만든 것이다. 그 사실을 코드에 남겨 두면 나중에 "이게 왜 5회인가"를 물을 수 있고, 답이 없으면 숫자를 고칠 수 있다.

"답변이 끝났다"는 DOM에서 관측할 수 없다. 그래서 페이지가 직접 말한다. `markAnswer('start' | 'done' | 'abort' | 'error')`. 마크가 없는 페이지도 폭주·끼어들기·중복은 감사되고, 침묵 규칙만 건너뛰며 리포트에 `completion: unmarked`라고 적힌다. **관측 불가능한 것을 통과로 처리하지 않는 것**이 계약의 일부다.

### 2.4 예산이 종료 코드가 된다

```bash
node dist/cli.js audit http://127.0.0.1:4319/good.html \
  --budget "announcements<8,words/min<400,no-partial,no-duplicate,no-silent"
```

위반하면 종료 코드 1. `bad.html`은 1, `good.html`은 0이다. 2편의 `diff --check`가 breaking에서 exit 3을 내는 것과 같은 발상이다. **리뷰 코멘트는 무시될 수 있지만 CI의 빨간불은 무시되지 않는다.** 접근성은 특히 그렇다. "이번엔 봐줘"가 한 번 통하면 그다음부터는 매번 통한다.

### 2.5 교정은 라이브러리 하나로 끝난다

계측만 하면 지적이고, 교정이 없으면 도구는 소음이다. 같은 패키지에 안내자를 넣었다.

```javascript
const announcer = createStreamingAnnouncer({ minIntervalMs: 600, maxAnnouncements: 2 });
markAnswer('start');

for await (const delta of stream) {
  el.append(delta);        // 화면에 보이는 답변 — 라이브 리전 아님
  announcer.push(delta);   // 문장 경계까지 버퍼링
}
markAnswer('done');
announcer.done();          // "Answer complete. N words." — 들려준 단어 수
```

설계에서 일부러 하지 않은 것이 네 가지다.

- **토큰이 아니라 문장 단위.** 완결된 생각일 때만 말한다. `maxChunkChars`(180자)로 구두점 없는 긴 꼬리만 예외 처리한다.
- **상한.** `maxAnnouncements: 2`는 수십 단어 답변을 3초 남짓에 다 낭독하는 일을 막는다. 도입부만 알리고 나머지는 읽을 수 있게 둔다.
- **assertive는 오류에만.** `error()`와 `abort()`만 끼어들고 상태는 그러지 않는다.
- **끝은 한 번뿐.** `done()`/`abort()`/`error()` 중 첫 호출만 통과한다.

마지막 항목은 0.1.1에서 고친 버그다. 처음 버전은 중단 뒤에 `done()`이 오면 "Answer complete"를 읽었다. 사용자는 실패를 성공으로 들었다. 지금은 종료 상태가 terminal이고, 새 답변은 `reset()` 없이는 시작하지 않는다. 테스트가 그 세 경우를 고정한다 — 반복 abort/error는 발화 1회, abort 뒤 done은 완료 문구 없음, reset 뒤에는 정상 완료.

**이 도구가 아닌 것**도 README 첫 부분에 적어 두었다. WCAG 적합성 판정이 아니고, 실제 스크린리더가 아니고, 크롤 감사가 아니고, 토큰 회계가 아니다. 여섯 규칙을 통과했다고 4.1.3을 통과한 것은 아니다. 이 문장을 빼면 도구는 자기가 재지 않는 것까지 보증하는 것처럼 읽힌다.

## 3. streamscope — 와이어를 녹화하고, 일부러 망가뜨린다

발화 계측은 사용자에게 도달한 것의 절반만 본다. 나머지 절반은 그 발화를 만든 **프레임**이다. 툴 인자가 반쯤 파싱된 채 도착하는 순간, 소켓이 62%에서 죽는 순간은 화면에 흔적을 남기지 않는다. 새로고침하면 사라지고, 아무도 재현하지 못한다.

`streamscope`는 앱과 모델 서버 사이에 리버스 프록시로 앉는다. 브라우저를 프록시 URL로 열면, 모든 응답이 파싱되면서 그대로 스트리밍되고 동시에 기록된다. 세션마다 파일 하나다.

```json
{"v":1,"kind":"meta","session":"chat-ai-sdk","adapter":"ai-sdk","framing":"sse","protocol":"ai-sdk"}
{"t_ms":0,"seq":0,"raw":"data: {\"type\":\"start\",\"messageId\":\"msg_demo_1\"}\n\n","event":{"type":"run-start","name":"start"}}
{"t_ms":0,"seq":1,"raw":"data: {\"type\":\"text-delta\",\"id\":\"msg_demo_1\",\"delta\":\"Sure — \"}\n\n","event":{"type":"text-delta","id":"msg_demo_1","delta":"Sure — "}}
{"t_ms":12,"seq":2,"raw":"data: {\"type\":\"tool-input-delta\",\"toolCallId\":\"call_track_1\",\"inputTextDelta\":\"{\\\"order\"}\n\n","event":{"type":"tool-call-delta","id":"call_track_1","argsDelta":"{\"order"}}
```

줄마다 `t_ms`, `seq`, `raw`(정규화된 와이어 프레임), `event`(정규화된 의미 이벤트)가 있다. `t_ms`는 첫 프레임으로부터의 밀리초이고 절대 줄어들지 않는다. 재생이 앱에 되돌려 쓰는 것은 `raw`다. 나머지 — 패널, 장애, 요약 — 는 `event` 위에서 동작한다.

어댑터는 여섯 가지를 감지한다. Vercel AI SDK의 UI message stream(`ai-sdk`), 그 legacy data stream(`ai-sdk-data`), SSE 위의 AG-UI(`ag-ui`), 그리고 `{type: ...}` 꼴의 범용 SSE/NDJSON(`generic`), `text/plain` 토큰 스트림, 단일 JSON 응답. 마지막 두 개가 특히 유용하다. 단일 JSON으로 응답하는 앱은 "스트림이 아예 없음"이 녹화 한 프레임으로 드러나고, 평문 토큰 스트림은 청크마다 `text-delta` 하나가 된다.

### 3.1 장애 DSL의 인덱스는 프레임 번호다

```
drop(3)                     프레임 #3 드롭
drop(2..5)                  프레임 #2부터 #5까지
dup(7)                      프레임 #7을 두 번 (중복 토큰 버그)
truncate_tool_args(12)      모든 툴 인자 조각을 12바이트로 — 반쯤 파싱된 JSON
disconnect_at(0.62)         프레임의 62% 지점에서, 터미널 이벤트 없이 연결 종료
error(429,5)                프레임 #0–#4는 유지하고 429로 실패
slow(800,3)                 프레임 #3 전에 800ms (멈춘 토큰)
reorder(2,5)                프레임 #2와 #5를 맞바꿈 (순서가 뒤집힌 툴 인자)
```

인덱스가 **녹화된 트레이스의 0부터 시작하는 프레임 인덱스**라는 점이 설계의 핵심이다. 그래서 장애를 적는 순서가 결과를 바꾸지 않는다. 적용 순서는 고정이다: `truncate → drop → dup → reorder → disconnect → error → slow`. 만약 적용 순서가 입력 순서를 따르면 `drop(3),dup(2)`와 `dup(2),drop(3)`이 다른 트레이스가 되고, 픽스처는 조용히 재현 불가능해진다. 잘못된 장애는 이유와 함께 실패한다 — `drop(99)`는 `out of range — the trace has 16 frame(s)`로 끝난다.

### 3.2 앱은 자기 엔드포인트와 대화한다고 믿는다

Playwright 픽스처가 이 도구를 테스트로 바꾼다.

```javascript
const stream = await replayStream(page, 'demo/traces/chat-ai-sdk.jsonl', {
  url: '**/api/chat*',
  inject: ['drop(3)', 'disconnect_at(0.62)'],
});
await page.goto('/');
await page.getByRole('button', { name: 'Send' }).click();
await expect(page.getByText('stream interrupted')).toBeVisible();
await expect(page.getByRole('status', { name: /tracking/ })).toHaveCount(1);
```

동작은 `page.route`와 `route.continue({ url })`뿐이다. 앱의 요청은 네트워크 계층에서 로컬 재생 서버로 재라우팅되고, 앱은 여전히 자기 `/api/chat`과 대화한다고 믿는다. 그래서 스트리밍, 중간 중단, 에러 프레임이 프로덕션과 같은 경로로 처리된다. 이 패키지에는 Playwright 의존성이 없다.

자격 증명 헤더(`authorization`, `cookie`, `set-cookie`, `x-api-key`, `proxy-authorization`)는 트레이스에 `[redacted]`로 저장된다. 녹화본은 커밋되는 물건이고, 커밋되는 물건에 세션 쿠키가 들어 있으면 그건 도구가 만든 사고다.

## 4. agent-ui-guard — 시간적 버그는 시간축에서만 잡힌다

페이지 안에서 계속 관측하면 스냅샷 문제가 사라진다. `agent-ui-guard`는 Playwright의 `addInitScript`로 페이지에 런타임을 심고, 모든 DOM 변경마다 상태를 샘플링한다.

```javascript
const start = () => {
  sample();
  const observer = new MutationObserver(() => {
    mutations += 1;
    sample();
  });
  observer.observe(document.documentElement, {
    subtree: true, childList: true, attributes: true,
    attributeFilter: ['aria-modal','aria-hidden','aria-busy','hidden','style','class','open',
                      contract.toolCallStateAttr, contract.turnStateAttr],
  });
  // MutationObserver misses nothing in the DOM, but a state that is painted
  // then removed between two mutation batches is still worth a periodic look.
  window.setInterval(sample, 150);
  window.addEventListener('pagehide', sample);
};
```

주석의 이유가 실제 이유다. 뮤테이션 배치 사이에 그려졌다 지워지는 상태가 있고, 150ms 주기 샘플이 그걸 잡는다. 정확성은 뮤테이션 옵저버가, 마지막 구멍은 타이머가 맡는다.

런타임은 `addInitScript(fn)`으로 넘기지 않고 **소스 텍스트**로 주입된다. esbuild(`tsx`)가 직렬화할 때 명명 함수 주위에 `__name(...)` 호출을 넣는데, 그 헬퍼는 페이지 안에 없다. 소스 문자열로 넣고 헬퍼를 stub하면 Vitest, Playwright, tsx에서 똑같이 동작한다. 사소한 호환성 문제처럼 보이지만, 이런 것이 하나 있으면 도구는 "내 환경에서는 되는데"로 시작한다.

### 4.1 불변식 다섯 개

| 불변식 | 실패 조건 |
|---|---|
| `singleModalAtATime` | 같은 순간에 모달이 둘 이상 보였을 때 — 한 프레임이라도 |
| `noStuckStreaming` | 스트리밍 구간이 `maxStreamMs`를 넘겼을 때 |
| `toolCallBalanced` | 툴 호출이 터미널 상태에 도달하지 못했을 때 — 턴이 먼저 끝났거나, 카드가 언마운트됐거나, `settleTimeoutMs` 뒤에도 running |
| `noConsoleOrPageErrors` | `console.error` 또는 잡히지 않은 예외 |
| `noHttp5xx` | 상태 500 이상 응답 |

각각은 평범한 객체다. 이름을 바꾸거나, 하나만 쓰거나, 조합할 수 있다. `always`는 매 스텝 후 평가되고, `eventually(...).within(10_000)`은 조건이 성립할 때까지 폴링한다. **데드라인은 "성립하지 않음"을 처음 확인한 시점부터 시작한다.** 그래서 몇 초 뒤에 도착하는 결과를 지켜볼 수 있다.

### 4.2 시드가 같으면 액션 시퀀스가 같다

퍼저(fuzzer)는 재현되지 않으면 쓸모없다. 드라이버는 가중치로 액션을 고르고, 파라미터도 같은 시드 PRNG에서 뽑고, 모든 스텝을 `trace.json`에 남긴다. `replayTrace`는 그 스텝을 다시 실행한다. 간헐적 버그가 결정적 버그가 된다.

실패한 실행은 다섯 개의 아티팩트를 남긴다.

```text
run-20261121-132129-seed7-failed/
├── trace.json       # 정확한 스텝 + 관찰값, 재생 가능
├── report.md        # 사람이 읽는 요약과 스텝 표
├── repro.spec.ts    # 녹화된 플랜이 채워진 Playwright 테스트
├── dom.html         # 실패 순간의 DOM
└── failure.png      # 전체 페이지 스크린샷
```

`repro.spec.ts`에서 고칠 곳은 하나다. `ACTIONS` import를 내 액션 정의로 바꾸면 나머지(URL, 시드, 플랜, 기대 불변식)는 이미 채워져 있다. **버그 리포트의 완성도는 도구가 정한다**는 생각으로 만들었다. 사람이 "그때 뭐 했더라"를 복원해야 하면 그 리포트는 절반만 쓸모 있다.

데모 픽스처는 일부러 망가진 네 가지 모드로 계약을 검증한다.

| 모드 | 주입되는 버그 | 잡는 불변식 |
|---|---|---|
| `double-modal` | 팔레트를 열어도 Settings가 열린 채 남음 | `singleModalAtATime` |
| `orphan-spinner` | `web.search`가 실행 중인데 턴이 닫힘 | `toolCallBalanced` |
| `stuck-streaming` | 인디케이터를 지우지 않은 채 스트림 종료 | `noStuckStreaming` |
| `http-500` | 두 번째 프롬프트가 500 반환 | `noHttp5xx` |

한계도 코드 옆에 적었다. 페이지 하나·탭 하나이고, Shadow DOM은 열린 루트만 본다. 런타임은 관측만 하고 고치지 않는다. 위반은 실행을 실패시킬 뿐 앱을 바꾸지 않는다. 타이밍 예산은 가장 느린 정상 스트림보다 넉넉하게 잡아야 하고, 특히 CI에서 그렇다.

## 5. proofshot — PR마다 "무엇이 나빠졌나"를 증거로

에이전트가 쓴 PR은 빠르고, 자기 설명은 산문이다. 리뷰어가 UI 변경에서 정말 답해야 하는 질문은 하나다. **지금 어떻게 보이고, 무엇이 나빠졌나.** Storybook과 Chromatic은 이 질문에 답할 수 있지만, 답하려면 모든 상태마다 스토리를 써야 하고 계정과 요금이 필요하다. 나는 그 비용을 내지 않기로 했다.

`proofshot`은 빌드 디렉터리 두 개 또는 URL 두 개를 받는다. 라우트는 diff에서 추론하고(`next-app`, `next-pages`, `react-router`, Vite/SPA, 정적 HTML), Playwright가 데스크톱·모바일 폭에서 전체 페이지를 찍고, `pixelmatch`가 변경 픽셀 비율과 diff PNG를 낸다.

```markdown
## 📸 proofshot

**1 changed · 1 unchanged · 0 failed** · **1 a11y regression** — `demo/before` → `demo/after`

| Route | Viewport | Pixel diff | a11y | Console | Status |
| --- | --- | --- | --- | --- | --- |
| `/` | desktop | **2.32%** | ⚠️ +4 | 0 → 1 | 🔴 changed |
| `/pricing` | desktop | **0%** | ✅ 0 | 0 | 🟢 unchanged |

**New issues**
- `img-alt` `section.hero > div.shot-row > img:nth-of-type(1)` — image has no alt attribute
- `button-name` `section.hero > div.actions > button.icon-only` — button has no accessible name
- `heading-order` `main > section.logos > h3` — heading jumps from h1 to h3
- `console-error` `console` — Acme Studio: GET /api/tokens returned 500
```

### 5.1 a11y 델타는 집합 차다

2편에서 링크를 점수가 아니라 저장된 행으로 다뤘던 것과 같은 원리다. 접근성 문제를 **개수**로 비교하면 "3개에서 3개로 그대로"라는 답이 나오고, 그 답은 쓸모없다. 무엇이 새로 생겼는지가 필요하다.

```javascript
export function computeA11yDelta(before, after) {
  const beforeKeys = new Set(before.issues.map(issueKey));
  const afterKeys = new Set(after.issues.map(issueKey));

  const regressions = after.issues.filter((issue) => !beforeKeys.has(issueKey(issue)));
  const fixes = before.issues.filter((issue) => !afterKeys.has(issueKey(issue)));
  // ...
  return { regressions, fixes, regressed: regressions.length > 0 || after.counts.consoleErrors > before.counts.consoleErrors };
}
```

`issueKey`는 규칙 이름·DOM 경로·세부 문구의 조합이다. 그래서 "같은 버튼의 alt 누락"은 같은 문제로 남고, "새로 생긴 다른 버튼의 alt 누락"은 회귀로 잡힌다. 검사기는 axe가 아니라 DOM만 쓰는 규칙 10종이다 — `img-alt`, `button-name`, `link-name`, `input-label`, `heading-order`, `duplicate-id`, `landmark-main`, `html-lang`, `page-title`, `console-error`.

### 5.2 리포트는 코멘트 하나를 계속 고친다

`report.md`는 안정적인 마커로 시작한다. 그래서 워크플로가 PR마다 새 코멘트를 쌓지 않고 이전 코멘트를 수정한다. 10번의 push가 10개의 "proofshot 결과" 코멘트를 남기면 리뷰 스레드는 읽을 수 없게 된다.

`--fail-on change,a11y,error`를 주면 해당 조건에서 종료 코드 1이다. 기본값은 0.1% 임계값이고, 그 아래는 노이즈다. 이 기본값을 정한 이유는 5.2절이 아니라 7절에 적었다.

## 6. assignment-map — 콘텐츠 파이프라인의 같은 게이트

채용 과제·이벤트를 매일 03:00에 수집하는 파이프라인이다. 여기서 "증거 없는 자동화"는 두 가지 모습으로 나타난다. **정책 판정이 조용히 틀리는 것**과 **디자인이 조용히 AI 티로 돌아가는 것**.

### 6.1 골든케이스 6/6이 아니면 커밋이 잠긴다

```javascript
const p = postings.find((x) => x.id === c.id);
if (!p) { fails.push(`GOLDEN ${c.id}: 데이터에서 실종 — 커밋 금지`); continue; }
if (E.company_includes) check(`GOLDEN ${c.id}`, p.company.includes(E.company_includes), `company=${p.company}`);
if (E.ai_policy) check(`GOLDEN ${c.id}`, p.ai_policy === E.ai_policy, `ai_policy=${p.ai_policy} (기대 ${E.ai_policy})`);
```

`golden_cases.json`은 확정 사례 여섯 개다. 채용 공고 네 개(올리브영 `required`, 크래프톤 `allowed_graded`, 무신사 `allowed_graded`, 더게임 `required`)와 이벤트 두 개(코파톤 `required` + 채용 링크, 그리고 하나 더). `validate.mjs`가 이 여섯 개를 재현하지 못하면 커밋이 잠긴다 — 스크립트가 "실종 — 커밋 금지"를 출력하고 non-zero로 끝난다.

왜 하필 여섯 개인가. **정책 판정은 LLM이 하고, 그 판정이 파이프라인의 진실이 되기 때문이다.** 판정 로직이나 프롬프트를 고쳤을 때 기존 판정이 뒤집히면, 그건 개선이 아니라 회귀다. 회귀를 잡는 데 필요한 것은 전체 데이터가 아니라 이미 정답을 아는 사례다. 여섯 개로 충분했고, 케이스가 시대에 뒤처지면 코드가 아니라 `golden_cases.json`을 먼저 고치고 사유를 커밋하게 되어 있다.

### 6.2 안티슬롭 16체크

디자인 규칙은 취향이 아니라 lint 대상이다. `web/scripts/slop-lint.mjs`는 `src/`와 `index.html`을 훑어 12개 금지 패턴과 4개 크래프트 요구를 본다.

```javascript
if (/gradient\(/i.test(all)) flag('gradient', ...);                          // 그라디언트
if (/background-clip:\s*text/i.test(all)) flag('gradient-text', ...);        // 그라디언트 텍스트
if (/(font-family|--mono)[^;\n]*(Inter|Roboto|Geist|system-ui)[,)]/i.test(all)) flag('overused-font', ...);
if (/backdrop-filter|text-shadow|filter:\s*drop-shadow/i.test(all)) flag('glass-glow', ...);
if (/letter-spacing:\s*0\.[1-9]\d*em/i.test(all)) flag('eyebrow', ...);       // 넓은 자간 라벨
for (const m of all.matchAll(/border-radius:\s*(\d+(?:\.\d+)?)px/g))
  if (parseFloat(m[1]) > 4) flag('radius', ...);                             // 4px 초과 라운드
```

금지 목록은 이렇다. 그라디언트, 그라디언트 텍스트, Inter/Roboto/Geist/`system-ui` 선행 폰트, 글래스모피즘·글로우·외부 drop-shadow, 이모지, 자간 0.1em 이상 라벨, 스톡 카피(`seamless`, `supercharge`, `unlock your`, `empower` …), fade-up 스크롤 리빌, `text-align: center`, 4px 초과 border-radius, ` · ` 구분자, `card`/`hero`/`glass`/`glow` 클래스명.

요구 목록은 `:focus-visible` 스타일, `prefers-reduced-motion` 대응, `name="viewport"`, 그리고 모든 `img` 요소의 `alt`다. 앞의 둘은 접근성이고, 뒤의 둘은 기본기다. **금지 12개와 요구 4개를 같은 린터에 넣은 이유**는, 안티슬롭이 "예쁘게"가 아니라 "기본기를 지킨 상태에서 안 튀게"이기 때문이다. AI가 만든 화면은 대개 아름답지 않은 게 아니라 기본기가 빠져 있다.

`npm run build`는 이 검사가 통과해야 다음 단계로 간다. 슬롭 체크 16종이 실패하면 배포가 나가지 않는다. 운영비는 0원이다 — GitHub Actions와 Pages의 무료 쿼터 안에서 수집·검증·배포가 다 돈다.

## 7. 내가 포기한 것

이 절이 이 글의 값이다. 게이트는 공짜가 아니다.

### 7.1 임계값을 만든 사람은 나다

1초에 5회, 250ms 버스트, 단어당 240ms, 픽셀 0.1%, 스트림 8초. 이 숫자는 측정에서 나왔지만 **자연 법칙이 아니다**. 정상 앱이 임계값 근처에서 흔들리면 나는 케이스가 아니라 숫자를 고치고 싶어진다. 그때마다 게이트는 조금씩 느슨해지고, 6개월 뒤에는 아무것도 잡지 못한다.

그래서 규칙을 둘로 나눴다. **숫자를 바꾸려면 왜 바꿨는지를 커밋에 남긴다. 규칙이 틀렸으면 코드가 아니라 규칙을 고친다.** 2편에서 골든케이스를 고칠 때 사유를 커밋하게 한 것과 같은 장치다. 임계값 유지보수는 이 도구들의 실질적인 운영비다.

### 7.2 시뮬레이션은 스크린리더가 아니다

세 프로필은 모델이다. 실제 NVDA를 켜고 들은 것이 아니다. 어떤 페이지는 세 프로필 전부에서 통과하고 실제 AT에서는 깨질 수 있다. 이 한계를 리포트에 매번 적는 이유는, 한 번이라도 "통과"를 "쓸 수 있음"으로 읽히게 하면 도구가 거짓말을 시작하기 때문이다. 실제 AT 검증은 여전히 사람이 해야 한다.

### 7.3 픽셀 diff는 노이즈와 싸운다

폰트 렌더링, 안티에일리어싱, 늦게 도착하는 이미지, 애니메이션의 마지막 프레임. 0.1% 임계값은 이런 것들을 걸러내지만, 걸러내는 동안 진짜 작은 회귀(테두리 1px, 색 대비 몇 단계)도 같이 걸러진다. `settleMs`와 `fullPage`로 절반은 줄었고, 나머지는 리뷰어가 diff PNG를 보는 몫으로 남겼다. **픽셀은 "달라졌다"를 증명하고 "나빠졌다"를 증명하지 않는다.**

### 7.4 퍼징은 확률이고, CI 시간은 유한하다

PR마다 시드 하나를 돌리고 야간에 시드 매트릭스를 돌린다. 그 구성은 **그 시드에서 안 나온 버그는 그날 안 나온다**는 뜻이다. 액션 가중치를 잘못 주면 특정 인터리빙은 영원히 안 나온다. 축소(shrinking)도 아직 없다. 위반 지점만 잘라내는 대신 실패한 트레이스 전체를 재생하는데, 40스텝 트레이스는 사람이 읽기에 길다.

### 7.5 미적 감각은 규칙 밖에 있다

16체크를 다 통과하고도 AI 티가 나는 화면이 있다. 규칙은 "이건 하지 마"이고, 감각은 "이건 이렇게 해"다. 후자를 린터로 옮기려는 시도는 대개 규칙이 아니라 취향의 독재가 된다. 그래서 slop-lint는 하한선이다. **하한선이 있는 것과 좋은 디자인은 다르고, 하한선이 없으면 좋은 디자인도 유지되지 않는다.**

### 7.6 코드 스타일을 제품 결정에 묶는 비용

`border-radius` 4px 초과 금지는 이 사이트의 결정이다. 다른 제품에 이 린터를 그대로 쓰면 제품 결정을 도구가 선점한다. middle-dot 구분자 금지도 마찬가지다. 이 규칙들은 그 프로젝트에서만 참이고, 그래서 패키지가 아니라 저장소 스크립트로 두었다.

## 8. 게이트를 어디에 두는가

네 도구는 서로 다른 층에 있다. 층이 다르면 잡는 버그도 다르고, 실패했을 때 할 일도 다르다.

| 층 | 도구 | 무엇을 고정하나 | 실패하면 |
|---|---|---|---|
| 계약 | `agent-ui-guard` | 세션 전체에서 항상 성립해야 하는 속성 | 인터리빙 버그 |
| 재현 | `streamscope` | 와이어 프레임 시퀀스와 장애 | 재현 불가 버그 |
| 측정 | `livesay` · `proofshot` | 발화 예산, 픽셀, a11y 델타 | 사용자 도달 품질 저하 |
| 규칙 | `slop-lint` · 골든케이스 | 디자인 하한선, 판정 회귀 | 배포 중단 |

순서가 중요하다. 계약이 먼저고 측정이 나중이다. 계약 없이 측정만 하면 "이번엔 4회니까 괜찮다"가 되고, 기준선이 사라진다. 반대로 측정 없이 계약만 있으면 "통과했으니 좋다"가 되고, 품질이 어디로 가는지 모른다.

그리고 1편의 문장으로 돌아온다. **게이트는 "나빠졌는가"만 판정하고, "좋은가"는 사람이 정한다.** 이 분업이 무너지면 둘 다 무너진다. 게이트가 좋음을 판정하려 들면 창의성이 죽고, 사람이 나빠짐을 판정하려 들면 아무도 매 PR마다 그 일을 하지 않는다.

세 편을 관통하는 주장은 하나다. **조용한 실패를 시끄러운 실패로 바꾸는 것.** 2편에서는 그것이 좌표와 종료 코드였고, 3편에서는 발화 횟수와 실패 아티팩트와 픽셀 비율이다. 셋 다 같은 형식이다 — 측정 가능한 숫자, 재현 가능한 사례, 실패하면 빨간불. 이 형식이 없으면 "잘 되는 것 같아요"가 유일한 품질 보고가 된다.

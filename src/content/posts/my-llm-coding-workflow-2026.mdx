# 나의 LLM 코딩 워크플로 — 2026년 말, 에이전트 데몬과 함께 일하는 법

올해 초 [Addy Osmani의 "My LLM coding workflow going into 2026"](https://addyosmani.com/blog/ai-coding-workflow)이 크게 화제였습니다. 계획 → 청크 단위 구현 → 교차 리뷰 → 잦은 커밋으로 정리된 그 글은 지금도 이 분야의 표준 참고서처럼 회자됩니다. 한국어 커뮤니티에서도 요약본이 돌았죠.

다만 읽으면서 든 생각은 "이건 도구를 잘 얹어 쓴 사람의 이야기"였습니다. 저는 작년부터 방향이 조금 달라졌습니다. 도구 위에 얹히는 워크플로를 다듬다가, 결국 **에이전트 도구 여럿을 묶는 층을 직접 만들기 시작**했습니다. 이 글은 그렇게 살아온 2026년 말의 제 워크플로입니다. 원칙은 Osmani와 많이 겹치지만, 실천 도구는 제 손으로 만든 것들이 섞여 있습니다.

## 1. 계획은 코드보다 먼저 쓴다 — spec과 Context Contract

에이전트에게 시키기 전에 `spec.md`를 먼저 씁니다. 요구사항, 경계 조건, 하지 말아야 할 것까지 적고, 에이전트에게 역질문을 반복시켜 빠진 조각을 채웁니다. Osmani가 인용한 "waterfall in 15 minutes"라는 표현이 정확합니다. 워터폴의 장점(명세)을 15분 안에만 하는 겁니다.

이 과정을 글로 정리한 게 [Context Contract로 산출물 품질 고정하기](/posts/frontend-ai-context-contract-playbook)입니다. 계약서 없이 에이전트를 돌리면, 결과물은 매번 다른 사람이 쓴 코드처럼 나옵니다.

## 2. 에이전트는 하나로 안 쓴다 — 듀얼 플랫폼

저는 Claude Code와 Codex를 같이 씁니다. 이유는 간단합니다. **모델마다 성격이 다르고, 실수하는 지점도 다르기 때문**입니다. 그래서 저의 기본 루프는 이렇습니다.

1. 구현은 주력 에이전트에게 — 컨텍스트를 잘 쌓아둔 쪽이 빠릅니다.
2. 리뷰는 다른 에이전트에게 — 코드를 쓴 모델이 자기 코드를 못 봅니다. 다른 모델의 눈이 필요합니다.
3. 둘의 의견이 갈리면 — 그 지점이 진짜 설계 결정이 필요한 곳입니다. 사람이 판단합니다.

플러그인, 스킬, 훅 같은 에이전트 설정 자체도 실험 대상입니다. Codex와 Claude Code 양쪽에서 돌아가는 워크플로 자산을 모아두니, 어느 쪽이 더 좋아져도 제 자산은 따라갑니다.

## 3. 세션 히스토리가 자산이 될 때 — 전문검색되는 대화 로그

워크플로 글들이 대부분 놓치는 게 이겁니다. **에이전트와의 대화는 자산인데, 대부분의 도구는 그걸 흘려보냅니다.**

작년에 이게 너무 답답해서 세션 저장소가 달린 데몬을 만들었습니다. 모든 에이전트 세션이 SQLite에 쌓이고 FTS5로 전문검색됩니다. 이제 이런 게 가능합니다.

```
$ damon search "storage format 변환기 라운드트립"

[0.42s] 214 sessions scanned
#0821  confluence-studio   "XHTML→Markdown 라운드트립 실패 케이스 정리"
#0793  confluence-studio   "quick-xml 파서로 매크로 문법 보존하기"
#0612  damon-core          "프로토콜 v2 스키마 설계 트레이드오프"
```

3개월 전에 에이전트와 씨름하며 찾았던 해결책을 검색어 하나로 다시 꺼냅니다. "기록은 자산이다"라고 블로그에서 매번 썼는데, 정작 대화 기록이 사라지는 걸 그냥 두고 있었던 거죠.

## 4. 권한 승인은 사람의 몫 — 릴레이되는 allow/deny

에이전트가 터미널에서만 일하지 않게 되면서 권한 모델이 중요해졌습니다. 제 원칙은 하나입니다. **파일 쓰기, 커밋, 네트워크 같은 파괴적 행위는 사람이 승인한다.** 승인 요청은 쓰고 있는 채널(웹 UI, CLI, 텔레그램 버튼)로 릴레이됩니다. 밥 먹으러 가는 길에 텔레그램으로 "이 커밋 날려도 될까요?"가 오면, 확인하고 버튼 하나로 승인합니다.

LLM을 "과신하고 실수에 취약한 주니어 개발자처럼 대하라"는 Simon Willison의 조언에 완전히 동의합니다. 저는 한 걸음 더 나아가, 그 주니어에게 프로덕션 키를 주지 않는 구조를 시스템으로 만들었습니다.

## 5. 커밋은 세이브포인트다 — worktree 병렬 실험

작업은 반드시 작은 청크로 쪼개고, 청크가 끝나면 테스트를 돌리고 커밋합니다. 게임의 세이브포인트와 같아서, 에이전트가 이상한 방향으로 갈 때마다 직전 커밋으로 돌아가면 됩니다.

실험이 두 개 이상 병렬로 필요할 때는 [Git Worktree로 병렬 브랜치 작업하기](/posts/git-worktree-parallel-branch-workflow)에서 다룬 대로 워크트리를 나눠서, 에이전트마다 각자의 워크트리에서 돌립니다. 서로의 변경사항을 오염시키지 않는 게 핵심입니다.

## 6. 검증은 여전히 내 일이다

아무리 생성이 빨라져도 검증의 책임은 사람에게 남습니다. 저는 세 가지를 고정적으로 돌립니다.

- **E2E Eval**: [Playwright 기반 E2E Eval 운영 가이드](/posts/frontend-ai-e2e-evals-playbook)대로 브라우저 시나리오를 게이트로
- **산출물 스코어카드**: [AI 산출물 검증 스코어카드](/posts/frontend-ai-delivery-scorecard-playbook)로 "또 왔네" 리뷰를 구조화
- **다른 모델의 교차 리뷰**: 2번에서 말한 듀얼 구조

## 남는 것 — 결국 클래식 엔지니어링

2년간 이렇게 일해본 결론은 Osmani와 같습니다. AI-augmented이지 AI-automated가 아닙니다. 오히려 계획, 계약, 테스트, 커밋 습관 같은 고전적인 엔지니어링 원칙이 에이전트 시대에 더 중요해졌습니다.

차이가 있다면, 저는 그 원칙을 문서가 아니라 **돌아가는 시스템으로** 만들기 시작했다는 것. 그 이야기는 다음 글에서 이어서 씁니다.

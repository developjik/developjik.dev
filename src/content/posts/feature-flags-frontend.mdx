# 피처 플래그로 안전하게 배포하기

## 개요

"목요일 밤에 배포했는데 금요일 아침에 롤백했다"는 이야기를 몇 번 하고 나서 팀에 피처 플래그를 도입했다. 피처 플래그(feature flag, feature toggle)는 기능을 코드 배포와 분리해서 켜고 끄는 스위치입니다. 도입 초반에는 정말 유용했지만 1년쯤 지나니 "이 플래그 꺼도 되나요?"라는 질문에 아무도 대답 못 하는 상황이 왔습니다. 이 글은 피처 플래그를 안전하게 쓰면서 부채로 만들지 않는 방법에 대한 회고입니다.

## 배포와 릴리스의 분리

플래그의 가장 큰 가치는 배포(deploy)와 릴리스(release)를 분리하는 것입니다. 코드는 이미 프로덕션에 있지만 사용자에게는 보이지 않고, 스위치 하나로 점진적으로 노출합니다.

- **카나리**: 1% → 10% → 50% → 100%로 트래픽을 늘려가며 영향을 확인.
- **즉시 롤백**: 문제 발견 시 롤백 배포(수 분)가 아니라 플래그 오프(수 초).
- **트렁크 기반 개발**: 장기 브랜치 대신 미완성 코드를 플래그 뒤에 두고 계속 main에 통합.

프론트엔드에서 가장 단순한 형태는 이렇게 생겼습니다.

```ts
type Flags = Record<string, boolean>;

async function getFlags(userId: string): Promise<Flags> {
  const res = await fetch(`/api/flags?user=${userId}`);
  return res.json();
}

function NewCheckout({ flags }: { flags: Flags }) {
  if (!flags["new-checkout"]) {
    return <LegacyCheckout />;
  }
  return <CheckoutV2 />;
}
```

여기에 사용자 비율, 코호트, 환경별 기본값 같은 타게팅 규칙이 붙으면 LaunchDarkly, Unleash, Flagsmith 같은 도구나 자체 서버의 영역이 됩니다.

## 수명주기: 태어나고, 켜지고, 죽는다

부채를 만들지 않는 핵심은 플래그에 수명주기가 있다는 걸 인정하는 것입니다. Martin Fowler의 토글 분류를 참고하면 용도별로 수명이 다릅니다.

- **릴리스 토글**: 점진적 출시용. 수명 몇 주. 가장 흔하고, 가장 흔히 방치된다.
- **운영 토글**(kill switch): 문제 있는 기능을 긴급히 끄는 회로 차단기. 수명 부정.
- **실험 토글**: A/B 테스트용. 실험 종료와 함께 제거.
- **권한 토글**: 유료 플랜처럼 영구적인 기능 게이트. 이것만 장기 생존이 정상.

저희 팀의 실패는 이 유형을 구분 없이 하나의 플래그 시스템에 섞어 넣은 것이었습니다. 실험 토글이 릴리스 토글 코드에 의존하게 되고, 실험을 지우려면 릴리스도 함께 건드려야 하는 상황이 생겼습니다.

## 기술부채가 되는 순간

플래그가 부채로 전환되는 신호는 꽤 명확합니다.

- 조합 폭발: 플래그 3개가 겹치면 코드 경로가 8가지. 테스트 매트릭스가 감당 불가능해집니다.
- 아무도 기본값을 못 바꿈: "이 플래그 끄면 무슨 일이 생기는지 모른다"는 상태가 6개월 지속.
- 죽은 코드의 축적: 항상 켜진 플래그는 `if (true)`와 같아서, 분기 안의 미사용 경로만 남습니다.

특히 프론트엔드에서는 플래그 뒤에 숨은 미사용 코드가 번들에 실려 들어가는 문제가 있습니다. 트리셰이킹은 빌드 타임 상수만 제거할 수 있어서, 런타임 평가되는 `flags["x"]` 분기는 두 경로 모두 번들에 포함됩니다.

## 정리 리듬: 플래그 제거도 기능이다

해결책은 단순했습니다. "플래그 제거도 완료 조건에 포함한다." 구체적인 리듬은 이렇습니다.

1. 플래그를 만들 때 이슈에 만료일(예: 4주)을 적는다.
2. 100% 안정화 후 1주일이 지나면 만료일이 지난 플래그가 주간 회의 안건에 자동으로 올라온다.
3. 제거 PR은 기능 PR만큼 우선순위를 받는다.

코드 정리는 기계적으로 합니다. 항상 참이 된 분기만 남기고 플래그 참조를 전부 삭제.

```diff
- function Checkout({ flags }: { flags: Flags }) {
-   if (!flags["new-checkout"]) {
-     return <LegacyCheckout />;
-   }
-   return <CheckoutV2 />;
- }
+ function Checkout() {
+   return <CheckoutV2 />;
+ }
```

코드 참조를 지운 뒤에야 플래그 설정(서버·대시보드)을 지우는 순서가 안전합니다. 반대로 하면 참조가 남은 채 기본값이 사라져 에러가 납니다.

## 관측: 플래그는 실험 도구이기도 하다

정리만이 전부가 아닙니다. 플래그로 트래픽을 나눴다면 나눈 만큼 측정해야 합니다. 저희는 플래그별로 에러율과 핵심 지표를 대시보드에 코호트로 나눠 보고, 카나리 단계에서 오류율이 기준을 넘으면 자동으로 플래그를 되돌리는 규칙을 둬습니다. "꺼두면 안전하다"가 아니라 "꺼야 한다는 신호를 시스템이 알려준다"로 바뀌었을 때 플래그 도구의 진짜 가치가 나온다고 느꼈습니다.

## 마무리

피처 플래그는 배포의 두려움을 줄여주는 훌륭한 도구이지만, 본질적으로 "나중에 청소하겠다"는 부채를 만드는 행위입니다. 수명주기를 유형별로 정하고, 만료일을 적고, 제거를 완료 조건에 넣는 리듬이 있어야 자산으로 남습니다. 플래그를 만들 때마다 "이 스위치는 언제 사라지나"를 함께 적어두는 것, 그 습관 하나가 1년 뒤의 코드베이스를 결정한다고 생각합니다.

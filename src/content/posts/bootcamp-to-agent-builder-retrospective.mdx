# 부트캠프에서 에이전트 빌더까지 — 프론트엔드 2년의 전환기 회고

블로그를 시작한 지 2년이 넘었다. 연말도 두 달 남짓 남은 시점이지만, 지금 회고를 쓰는 이유는 단순하다. **요즘 내 git log를 보면 내가 1년 전의 나와 다른 일을 하고 있어서**다. 언제 어떻게 바뀌었는지, 기록이 남아 있으니 정리해본다.

회고의 재료는 감상이 아니라 저장소와 글이다. 지금 내 GitHub에는 저장소 13개가 있고, 블로그에는 글이 70편을 넘었다. 이 둘을 시간순으로 늘어놓으면 전환의 지점들이 선명하게 보인다.

## 1년차: 완전 가이드의 시절

2024년, 블로그를 시작했다. 부트캠프를 마치고 프론트엔드 개발자로 일하면서, 배우는 것들을 그대로 글로 쌓았다. 지금 블로그의 절반이 그 시절의 글이다.

- JavaScript `this` / 프로토타입 / 이벤트 루프 완벽 가이드
- AWS EC2 / IAM / Lambda 완전 가이드
- Git Flow / GitHub Flow / Trunk-based 이해하기

"완전 가이드"라는 제목에서 알 수 있듯, **체계적으로 정리하는 것**이 나의 학습 방식이었다. 이 글들이 검색 유입을 꾸준히 가져다줬고, 글쓰기 습관도 이때 잡혔다. 나쁜 시기가 아니었다. 다만 지금 돌아보면 이런 글은 누구나 쓸 수 있는 글이었다. 시장에 이미 수십 개씩 있는 주제를, 내 방식으로 다시 정리한 것뿐이었다.

## 전환점: "AI가 코드를 쓰면, 내 일은 뭐지"

2025년부터 조급해졌다. Copilot이 절반을 쓰고, 이듬해엔 에이전트가 브랜치를 파고 커밋을 하는 시대가 왔다. 코딩 테스트도, 레거시 마이그레이션도, 리뷰도 에이전트가 한다. 그때 내 결론은 이랬다.

> 생성이 저렴해지면, 검증과 운영이 비싸진다. 나는 비싼 쪽에 있어야 한다.

이 문장이 지금의 블로그 헤더 — "AI가 코드를 쓰는 시대에 개발자의 일은 검증과 운영으로 옮겨갑니다" — 가 됐고, [이직에 바로 쓰는 프론트엔드 AI 실무](/series/frontend-ai-ops) 시리즈 24편의 뼈대가 됐다. E2E Eval, 온콜 드릴, 변경 실패율 관리, 공급망 대응. 전부 "생성이 아닌 검증" 이야기다.

그런데 시리즈를 쓸수록 한계가 보였다. **나는 처방을 쓰고 있는데, 처방의 근거가 될 실전 기록이 없었다.**

## Python에서 Rust로: 도구가 제품이 되는 순간

전환의 물리적 신호는 저장소에서 먼저 나타났다.

Confluence를 쓰면서 매주 반복하던 문서 내보내기를 Python GUI 도구(`confluence-export-desktop`)로 만들었다. 잘 썼다. 그런데 기능이 자라면서 — Markdown 편집, 예약 내보내기, AI 채팅이 붙으면서 — Python 스크립트 모음으론 한계가 왔다. 그래서 옮겼다. `confluence-studio`. Tauri 2 + Rust + React 19.

프론트엔드 개발자가 Rust를 선택한 건 낭만이 아니라 계산이었다.

- 상주해서 도는 스케줄러와 내보내기 워커의 안정성
- OS 키체인(API 토큰) 접근이 1급 기능
- Electron 없이 가벼운 네이티브 배포

그리고 무엇보다, **내가 에이전트로 Rust를 배울 수 있는 시대**였다. 새 언어 진입 비용이 낮아진 것 자체가 에이전트 시대의 수확이다.

## 결국 에이전트를 묶는 층을 만들다

confluence-studio에 AI 채팅을 붙이면서 여러 코딩 에이전트 CLI를 돌려봤다. 그리고 똑같은 문제에 매번 부딪혔다. CLI마다 세션, 권한, 히스토리가 제각각이라는 것. 같은 질문을 세 번 하게 되고, 지난 대화는 사라진다.

"이건 도구의 문제가 아니라 층(layer)이 없는 문제다."

그렇게 `damon-agent-core`를 시작했다. 하나의 로컬 데몬이 에이전트 CLI 9개를 통합 제어하고, 세션은 SQLite에 쌓아 전문검색하고, 권한 승인은 사람이 쓰는 채널로 릴레이한다. 120커밋쯤 쌓였고, 크로스플랫폼 CI와 배포까지 갖췄다. 프로필 README를 꾸며주는 것도 내 에이전트다. "사람은 설계하고, 에이전트가 일한다"가 슬로건이 아니라 진짜 생활이 됐다.

블로그도 마찬가지였다. Nextra로 시작한 블로그를 Astro 5로 갈아엎고, 에이전트 시대 시니어 블로그에 맞게 재설계했다. 이 마이그레이션 조차 에이전트와 함께 했다.

## 2년의 정리 — 무엇이 바뀌었고 무엇이 안 바뀌었나

바뀐 것:

- **학습의 대상**: 프레임워크 API → 검증·운영·오케스트레이션 설계
- **언어의 영역**: TypeScript 하나 → Rust와 병행
- **산출물**: 정리 글 → 돌아가는 시스템
- **에이전트의 위치**: 자동완성 도구 → 함께 일하는 주체

안 바뀐 것:

- **기록은 자산이다.** 글 66편, 세션 로그 수천 개. 쌓아둔 기록이 다음 결정의 재료다.
- **작게 자주 배포한다.** 데몬도 블로그도 작은 커밋의 연속이다.
- **검증은 생성보다 비싸다.** 2년 전 내 결론은 지금도 유효하고, 앞으로도 그럴 것 같다.

# 코딩 에이전트 도구 지형도

## 개요

2026년의 코딩 에이전트 도구는 "어떤 게 제일 좋냐"로 답하기 어려울 만큼 분화했습니다. 저는 도구를 우열이 아니라 범주로 구분하고, 작업 유형에 따라 갈아타는 전략을 씁니다.

## 범주로 보는 도구 지형

제 기준으로 코딩 에이전트는 세 범주로 나뉩니다.

- **인라인 어시스턴트**: GitHub Copilot류. 에디터 안에서 다음 줄·다음 블록을 완성. 흐름이 끊기지 않는 게 강점
- **AI 네이티브 에디터**: Cursor류. 코드베이스 전체를 컨텍스트로 참조하고 채팅·인라인 편집·에이전트 모드를 갖춤
- **터미널 에이전트**: Claude Code류. 셸에서 동작하며 파일 읽기·쓰기·명령 실행까지 연속으로 수행. 테스트 실행 후 결과를 보고 수정하는 루프가 가능

범주마다 상호작용 단위가 다릅니다. 줄, 파일, 그리고 작업(task)입니다.

## 선택 기준

어떤 도구를 주력으로 할지 정할 때 보는 기준입니다.

1. **작업 단위**: 짧은 완성이 많은가, 파일 단위 리팩토링이 많은가, 멀티 파일 변경이 많은가
2. **검증 루프**: 도구가 테스트 실행 결과를 스스로 보고 고칠 수 있는가
3. **컨텍스트 통제**: 어떤 파일이 컨텍스트에 들어가는지 제어·확인할 수 있는가
4. **팀 표준**: 프롬프트·규칙 파일을 공유하기 쉬운 형태인가

## 병행 사용 전략

저는 세 범주를 작업 크기에 따라 병행합니다.

```text
짧은 완성·보일러플레이트  → 인라인 어시스턴트
파일 단위 리팩토링        → AI 네이티브 에디터
멀티 파일 기능 추가 + 테스트 루프 → 터미널 에이전트
```

예를 들어 타입 정의 몇 개 추가는 인라인으로, 어떤 컴포넌트의 props 정리는 에디터에서, "이 기능 추가하고 테스트까지 통과시켜줘"는 터미널 에이전트에 맡깁니다. 공통 규칙은 프로젝트 루트의 규칙 파일 하나로 통일해서 어느 도구를 쓰든 같은 컨벤션을 따르게 합니다.

## 주의점

- 에이전트가 연속으로 파일을 수정할수록 변경 분량이 커집니다. 커밋 단위를 작게 유지해야 되돌리기 쉽습니다.
- 컨텍스트 예산은 유한합니다. 관련 파일만 열어두는 습관이 응답 품질을 지킵니다.
- 도구마다 기본 동작(자동 수정 범위, 권한)이 다르므로, 처음 쓰는 도구는 읽기 위주 작업부터 검증합니다.

## 마무리

도구 지형은 계속 바뀌지만 범주별 사고방식은 유지될 것이라 봅니다. 하나의 도구에 충성하기보다, 작업 단위에 맞춰 범주를 고르고 규칙 파일로 일관성을 유지하는 것이 지금의 제 전략입니다.

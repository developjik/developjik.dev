# 에이전트가 조작하는 웹을 설계하는 법 — AI Native 프론트엔드 실무 가이드

"AI라는 소행성이 강타한 프론트엔드 웹 개발"이라는 번역 글이 올해 한국 커뮤니티를 몇 바퀴 돌았습니다. 그 글의 핵심 중 하나가 기억에 남습니다. **에이전트와 하네스(검증 도구)는 React/SPA를 선호한다**는 관찰이었죠.

왜일까요? 생각해보면 답이 단순합니다. 에이전트는 브라우저를 "봅니다". DOM을 읽고, 요소를 클릭하고, 상태가 바뀌길 기다립니다. 그런데 이제 그 브라우저를 조작하는 주체가 사람만이 아니게 됐습니다. **프론트엔드의 새로운 사용자(user agent라는 말이 문자 그대로 실현된)는 에이전트**입니다.

이 글은 제품을 "에이전트가 조작 가능한 웹"으로 만드는 실무 관점을 정리합니다. 결론부터 말하면 — **에이전트 친화적 웹은 접근성 친화적 웹이고, 그것은 결국 사람에게도 좋은 웹**입니다.

## 1. 에이전트는 접근성 트리로 웹을 본다

에이전트가 스크린리더 사용자와 닮았다는 관찰에서 시작합니다. 스크린리더는 시각적 렌더링이 아니라 **접근성 트리(accessibility tree)**를 읽습니다. 에이전트도 마찬가지입니다. Playwright 같은 도구로 DOM을 읽을 때, 시각적 배치보다 역할(role)과 이름(name)으로 요소를 식별합니다.

```html
<!-- 에이전트에게 이건 "무언가"다 -->
<div class="sc-jSgupP kQxjJB" onclick="submit()">제출</div>

<!-- 에이전트에게 이건 "제출 버튼"이다 -->
<button type="submit">제출</button>
```

위쪽은 CSS-in-JS 해시 클래스로 사람도, 에이전트도, 테스트도 식별할 수 없습니다. 아래쪽은 이름과 역할이 있습니다. [접근성 회귀를 막는 프론트엔드 PR 체크리스트](/posts/frontend-accessibility-regression-checklist)에서 반복해서 다뤘던 원칙이 에이전트 시대에 그대로 회수되는 순간입니다.

## 2. 조작 가능성 — 시맨틱 HTML이 인터페이스다

에이전트가 폼을 채우려면 필드가 "무엇인지" 알아야 합니다.

```html
<!-- 이름을 알 수 없는 입력 -->
<div class="field">
  <div class="label">이메일</div>
  <input class="sc-bXevnB" />
</div>

<!-- 이름이 계약된 입력 -->
<div class="field">
  <label for="email">이메일</label>
  <input id="email" name="email" type="email" autocomplete="email" />
</div>
```

`label`과 `input`의 연결, `type`, `autocomplete` 속성은 에이전트에게 계약(contract)입니다. "이 필드는 이메일이고, 브라우저 자동완성이 안다"는 정보를 주면 에이전트는 추측하지 않습니다. 추측이 사라지는 만큼 폼 자동화 성공률이 올라갑니다.

실무 원칙: **`div`에 onclick을 다는 순간, 그 요소는 에이전트에게 존재하지 않는다**고 생각하세요.

## 3. 예측 가능한 셀렉터 — data-testid와 디자인 토큰

에이전트가 UI를 조작하고 검증하려면 요소를 다시 찾을 수 있어야 합니다. 안정적인 식별자 전략은 세 층입니다.

1. **역할 + 이름**: `getByRole('button', { name: '제출' })` — 가장 사람에 가까운 식별
2. **라벨/플레이스홀더**: 폼 요소의 1차 식별자
3. **`data-testid`**: 시맨틱 식별이 불가능한 마지막 수단

CSS 클래스는 식별자가 될 수 없습니다. 스타일링 목적이기 때문에 리팩터링마다 변하거든요. 여기서 [디자인 시스템 변경을 안전하게 배포하는 법](/posts/frontend-ai-design-system-safe-rollout-playbook)과 연결됩니다 — 토큰 기반으로 스타일을 관리하면, 클래스명 변경이 구조 변경과 분리되어 에이전트의 셀렉터가 덜 흔들립니다.

## 4. URL로 도달할 수 있는 상태

에이전트는 주소창이 입구입니다. 상태가 URL에 있으면 에이전트는 클릭 7번 대신 URL 1번으로 도달합니다.

```text
❌ /dashboard (모든 것이 클라이언트 상태)
✅ /dashboard?tab=billing&range=30d
```

- 필터, 탭, 검색어 같은 **공유 가능한 상태는 URL에**
- 라우팅은 히스토리 API로 — 새로고침에 살아남는 상태만 진짜 상태
- 딥링크가 되는 화면은 에이전트가 "북마크"할 수 있는 화면입니다

SPA가 에이전트에게 유리하다는 관찰의 이면에는 이런 것들이 있습니다. 상태 전환이 프로그래밍 가능하다는 거죠.

## 5. 검증 가능성 — E2E 테스트는 에이전트의 안전망

에이전트가 코드를 고치면, 고친 코드가 여전히 웹을 올바르게 조작하는지 확인해야 합니다. 이건 사람이 할 수 없는 영역이라 자동화가 답입니다. [Playwright 기반 E2E Eval 운영 가이드](/posts/frontend-ai-e2e-evals-playbook)와 [브라우저 테스트 에이전트 릴리즈 게이트](/posts/frontend-ai-browser-testing-release-gate-playbook)에서 다룬 대로, 시나리오를 릴리즈 게이트로 돌리면 에이전트의 UI 회귀를 기계가 잡아줍니다.

핵심 전도: **E2E 테스트는 "사람 대신 확인하는 도구"에서 "에이전트를 견제하는 계약"이 됐습니다.**

## 6. 실무 체크리스트

| 관점 | 질문 | 통과 조건 |
| --- | --- | --- |
| 인식 | 주요 액션 요소가 역할+이름을 갖는가 | 버튼/링크/입력이 시맨틱 요소다 |
| 폼 | 모든 입력이 label과 연결됐는가 | `label for` 또는 `aria-labelledby` |
| 식별 | 셀렉터가 리팩터링에 살아남는가 | role/label 우선, `data-testid` 예비 |
| 상태 | 필터/탭이 URL에 반영되는가 | 붙여넣은 URL이 같은 화면을 연다 |
| 대기 | 비동기 로딩에 안정적 신호가 있는가 | 스켈레톤/aria-live, 임의 sleep 금지 |
| 검증 | 핵심 여정이 E2E로 묶였는가 | 에이전트 PR도 게이트를 통과해야 한다 |

## 마무리 — 부메랑으로 돌아온 접근성

에이전트를 위한 웹을 만들다 보면 결국 2019년의 접근성 가이드로 돌아옵니다. 시맨틱 HTML, 라벨, 안정적 식별자, 예측 가능한 상태. AI가 웹을 "보는" 방식이, 오래전부터 표준이 권장하던 방식과 수렴한 겁니다.

차이가 있다면 실천의 이유입니다. 예전엔 윤리와 규제라면, 지금은 **그게 자동화 성공률이고 배포 속도**입니다. 동기가 강해진 만큼, 이번엔 진짜 지켜질 것 같습니다.

# 접근성은 선택이 아니라 기본값이다

## 개요

"나중에 접근성 작업하자"는 말은 대부분 "영영 안 한다"는 뜻이라는 걸 프로젝트를 몇 번 하고 나서 알았습니다. 접근성은 나중에 덧붙이는 게 아니라 마크업을 짜는 순간부터 결정되기 때문입니다. 이번 글에서는 비용을 크게 올리지 않으면서 접근성을 기본값으로 만드는 방법을 정리합니다.

## 시맨틱 HTML이 절반 이상이다

접근성 작업의 대부분은 특별한 도구가 아니라 올바른 HTML입니다. 버튼이면 `button`, 제목이면 `h1`~`h6`, 목록이면 `ul`/`ol`, 탐색이면 `nav`를 쓰는 것만으로 스크린리더 사용자는 페이지 구조를 파악할 수 있습니다.

```html
<!-- 나쁜 예: 동작과 의미가 모두 사라진 마크업 -->
<div class="btn" onclick="submit()">제출</div>

<!-- 좋은 예: 의미, 키보드 동작, 폼 제출이 기본 제공 -->
<button type="submit">제출</button>
```

`button`은 엔터·스페이스로 활성화되고, 포커스를 받고, `disabled` 상태를 보조 기술에 알립니다. `div`에 클릭 핸들러를 단 코드는 이 모든 것을 직접 구현해야 하는데, 대부분 빠져 있었습니다. 실제 코드 리뷰에서 가장 자주 지적했던 것도 이 패턴이었습니다.

## ARIA는 필요할 때만

ARIA는 아무것도 없는 곳에 의미를 더하는 도구이지, 시맨틱 HTML의 대체재가 아닙니다. W3C의 ARIA 첫 규칙도 "필요하면 ARIA를 쓰지 말고 HTML을 바꿔라"입니다. ARIA는 잘 쓰면 유용하지만, 역할을 잘못 부여하면 스크린리더 사용자에게 아무 정보 없는 요소보다 더 혼란스럽습니다.

```html
<!-- 피할 패턴: div에 역할을 입히기 -->
<div role="button" tabindex="0" onkeydown="handleKey(event)">메뉴 열기</div>

<!-- 권장 패턴 -->
<button aria-expanded="false" aria-controls="menu">메뉴 열기</button>
```

정말 ARIA가 필요한 대표적인 경우는 커스텀 위젯입니다. 예를 들어 탭 인터페이스를 직접 만든다면 `role="tablist"`, `role="tab"`, `role="tabpanel"`과 `aria-selected`로 상태를 알려야 합니다. 하지만 그 전에 네이티브 요소나 검증된 라이브러리로 같은 결과를 낼 수 있는지 먼저 검토합니다. 직접 만드는 순간 키보드 동작, 포커스 관리, 상태 공지를 모두 책임져야 하기 때문입니다.

## 키보드로 다 접근 가능한가

키보드 순회 테스트는 도구 없이도 할 수 있는 가장 싼 접근성 검사입니다. 마우스에 손을 대지 않고 Tab, Shift+Tab, Enter, Space, Esc만으로 페이지 전체를 돌아봅니다. 확인할 항목은 이렇습니다.

1. 모든 인터랙티브 요소에 포커스가 도착하는가
2. 포커스 순서가 시각적 순서와 일치하는가
3. 포커스 링이 보이는가 (`outline: none`을 덮어쓰지 않았는가)
4. 모달을 열면 포커스가 안에 들어가고, Esc로 닫히며, 닫힌 뒤 원래 요소로 돌아오는가

실수가 자주 발생하는 지점은 모달과 드롭다운입니다. 포커스가 모달 밖으로 나가 버리면 키보드 사용자는 뒷배경을 탐색하게 되고, 닫아도 포커스가 `body`로 버려지면 위치를 잃습니다. 닫힐 때 열었던 버튼으로 포커스를 돌려주는 것까지 구현해야 기본값에 도달합니다.

## 스크린리더로 직접 테스트하기

자동 검사(ax, Lighthouse)는 문제의 일부만 잡습니다. 결국 사람이 들어봐야 합니다. macOS에는 VoiceOver가 기본 탑재되어 있어 Command+F5로 켤 수 있고, iOS 기기에서도 설정 > 접근성에서 켤 수 있습니다. Windows 사용자라면 NVDA가 무료입니다.

VoiceOver로 처음 들어보면 가장 충격적인 것은 페이지를 "읽는" 순서와 방식입니다. 이미지에 대체 텍스트가 없으면 "이미지"라고만 읽히고, 아이콘 버튼에 이름이 없으면 그냥 "버튼"입니다.

```html
<!-- 이름이 없는 버튼: 스크린리더는 "버튼"이라고만 읽는다 -->
<button onClick={toggleMute}>
  <svg aria-hidden="true"><!-- 아이콘 --></svg>
</button>

<!-- 이름을 제공한다 -->
<button onClick={toggleMute} aria-label="음소거">
  <svg aria-hidden="true"><!-- 장식용 아이콘은 보조 기술에서 제외 --></svg>
</button>
```

장식용 요소는 `aria-hidden="true"`로 제외하고, 의미 있는 그래픽은 대체 수단을 제공하는 것이 기본 원칙입니다.

## 마무리

접근성을 기본값으로 만드는 일은 특별한 기술이 아니라 습관에 가깝습니다. 시맨틱 요소를 먼저 고르고, ARIA는 네이티브로 안 될 때만, 키보드로 한 바퀴 돌아보고, 스크린리더로 한 번 들어보기. 이 네 가지가 PR 템플릿에 들어간 순간 팀의 기본값이 바뀌기 시작했습니다. 화면을 보지 않는 사용자뿐 아니라, 키보드만으로 일하는 사람, 일시적으로 팔을 다친 사람 모두를 위한 것이 접근성입니다.

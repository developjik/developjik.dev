# Tauri 2.0 vs Electron 완벽 비교: 아키텍처부터 선택 기준까지

## 어떤 문제를 푸는 도구인가

웹 기술로 데스크톱 앱을 만든다는 아이디어는 Electron이 이미 증명했습니다. VS Code, Slack, Discord가 보여주듯 HTML/CSS/JS로 네이티브급 앱을 만들 수 있다는 것은 이제 상식입니다. 그렇다면 Tauri는 왜 등장했을까요. 짧게 말하면 **"번들 크기와 리소스 사용량이라는 Electron의 구조적 대가"를 줄이면서, 같은 웹 프론트엔드 자산을 그대로 쓰는 길**을 제시하기 위해서입니다.

[Tauri 2.0 정식 릴리스(2024년 10월)](https://tauri.app/blog/tauri-20/)는 여기에 모바일(iOS/Android)까지 무대를 넓힌 메이저 버전입니다. 이 글은 두 프레임워크를 아키텍처·리소스·보안·생태계·이관 난이도 순서로 비교하고, 마지막에 선택 기준 체크리스트를 남깁니다. 데스크톱 도구를 만들 기회가 생겨 두 후보 사이에서 고민 중이라면 끝까지 읽어 보시면 좋겠습니다.

## 아키텍처 비교: 시스템 WebView vs 번들 Chromium

차이의 출발점은 "브라우저 엔진을 어디서 얻느냐"입니다.

- **Electron**은 앱에 [Chromium과 Node.js를 함께 포장](https://www.electronjs.org/docs/latest/)합니다. 렌더러 프로세스가 곧 Chromium이고, 메인 프로세스가 Node.js 런타임입니다. 어떤 OS에서도 동일한 브라우저 버전이 돌아가는 것이 최대 강점입니다.
- **Tauri**는 프론트엔드를 [운영체제의 시스템 WebView](https://tauri.app/blog/tauri-20/)에서 띄우고, 앱 코어는 Rust로 작성합니다. Windows에서는 WebView2(Edge 기반), macOS에서는 WKWebView, Linux에서는 WebKitGTK를 사용합니다. 배포물에는 Chromium이 들어가지 않습니다.

이 구조적 선택은 곧바로 트레이드오프로 이어집니다. Tauri 방식은 OS별 WebView 엔진이 다르므로 렌더링·API 차이를 직접 감당해야 하고, Electron 방식은 일관성을 사는 대가로 모든 앱이 자기 Chromium을 배송합니다.

## 리소스 비교: 번들 크기·메모리·시작 시간

"설치 용량과 메모리를 크게 줄인다"는 Tauri의 대표 주장은 구조적으로 자명합니다. Chromium과 Node.js를 번들하지 않으니 설치 크기의 하한이 다르고, 별도 Chromium 프로세스 트리를 띄우지 않으니 메모리 프로파일도 다릅니다. WebView2는 [Evergreen 배포 모드](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)로 OS에 설치·갱신되는 공유 런타임이라 앱이 직접 들고 다닐 필요가 없습니다.

다만 **구체적 수치는 조심스럽게 다뤄야 합니다**. 두 프로젝트 모두 "공식 벤치마크 수치"를 릴리스 문서로 발표하고 있지 않고, 제3자 벤치마크는 앱 구성·측정 환경(특히 시스템 WebView의 워밍업 여부)에 따라 편차가 큽니다. 그래서 이 글에서는 숫자를 인용하는 대신 판단 기준만 정리합니다.

- **설치 크기**: WebView 엔진을 번들하지 않는 Tauri가 구조적으로 유리. Electron 앱의 최소 크기는 번들된 Chromium+Node 크기의 하한에 묶입니다.
- **메모리**: Tauri가 시스템 WebView를 쓰면 통상 유리하지만, 사용자가 이미 브라우저를 띄워 놓은 환경에서는 WebView 공유 여부에 따라 격차가 좁아질 수 있습니다.
- **시작 시간**:두 후보 모두 최신 하드웨어에서 충분히 빠르며, 실제 격차는 번들 크기·코드 분할·초기 화면 복잡도가 좌우합니다.

요컄대 "Tauri = 가볍다"는 방향성은 맞지만, 프로젝트 의사결정에는 근사치가 아니라 자기 앱의 실측이 필요하다는 것이 제 결론입니다.

## Tauri 2.0의 모바일 지원

2.0의 가장 큰 변화는 iOS와 Android 지원입니다. 공식 발표에 따르면 Rust 코어를 모바일 OS의 네이티브 언어(Swift, Kotlin)로 감싸는 인터페이스를 만들어, 기존 Swift/Kotlin 코드 자산을 플러그인 형태로 재사용할 수 있게 했습니다. 개발 중에는 에뮬레이터와 실기기에서 핫 모듈 리플레이스먼트(HMR)도 돌아갑니다.

주의점은 플러그인 지원 범위입니다. 일부 공식 플러그인은 모바일에 맞지 않거나 아직 구현이 안 된 상태이며, 데스크톱 대비 개발자 경험도 프로젝트 스스로 "만족스럽지 않다"고 밝힌 만큼 성숙도가 낮습니다. 바코드 스캔·바이오메트릭·NFC 같은 모바일 전용 플러그인은 반대로 모바일에서만 쓸 수 있습니다. "하나의 UI 코드베이스로 데스크톱+모바일"이라는 슬로건은 사실이지만, 플러그인 호환 매트릭스는 시작 전에 반드시 확인해야 할 체크 항목입니다.

요컨대 "Tauri = 가볍다"는 방향성은 맞지만, 프로젝트 의사결정에는 근사치가 아니라 자기 앱의 실측이 필요하다는 것이 제 결론입니다.

### Tauri: permissions → scopes → capabilities

Tauri 1.x의 allowlist는 코어 API 일부만 통제할 수 있어 한계가 있었습니다. 2.0은 이를 걷어내고 세 개 논리로 재설계했습니다. [permissions](https://v2.tauri.app/security/permissions/)(명령 단위 on/off), [scopes](https://v2.tauri.app/security/scope/)(명령 인자 검증, 예: 접근 허용 디렉터리), [capabilities](https://v2.tauri.app/security/capabilities/)(어떤 창·웹뷰에 권한을 붙일지)입니다. 프론트엔드 WebView의 IPC 호출은 설정된 capability를 통과할 때만 Rust 커맨드에 도달합니다.

```json
{
  "identifier": "main-window",
  "description": "메인 창에는 최소 권한만 부여",
  "windows": ["main"],
  "permissions": ["core:default", "fs:default"]
}
```

여기에 더해 [외부 보안 감사](https://tauri.app/blog/tauri-20/)(Radically Open Security 수행, NLnet/NGI 펀딩)가 RC 단계에 공개됐고, 감사 결과로 개발 서버 노출 방식과 `fs`/`http` 플러그인의 스코프 검증이 강화됐다는 것도 공식 발표가 확인해 주는 사실입니다. IPC 자체도 재작성되어, 이전에는 모든 페이로드를 JSON으로 직렬화하던 것과 달리 대용량 데이터를 raw payload로 주고받을 수 있게 됐습니다.

### Electron: 프로세스 경계와 CSP

[Electron 보안 가이드](https://www.electronjs.org/docs/latest/tutorial/security)가 강조하는 기본기는 Tauri와 방향이 같습니다. `contextIsolation` 활성화, 프리로드 스크립트로 최소 API만 노출, Content Security Policy 적용, 원격 콘텐츠 신뢰 금지. 차이는 이 기본기의 상당 부분이 "개발자의 선택"이라는 점입니다. Electron은 Node.js 권한이 강력한 만큼 잘못된 설정의 폭발 반경이 크고, Tauri는 권한 시스템이 구조적으로 기본 잠금 상태에서 시작합니다. 어느 쪽이든 "설정이 곧 보안"이라는 점은 동일합니다.

## 생태계와 기존 자산 이관 난이도

### 플러그인 생태계

Tauri 2.0은 파일 시스템·HTTP·업데이트·클립보드·알림 같은 기능을 [공식 플러그인](https://tauri.app/blog/tauri-20/)으로 분리해 코어를 슬림하게 유지합니다(1.x의 `tauri::api` 모듈은 제거됨). 접근 권한도 플러그인 단위로 부여하므로 "쓰는 만큼만 권한"이 자연스럽게 됩니다. 반면 Electron의 Node 생태계는 npm 전체이며, 네이티브 모듈(.node)까지 동작합니다. 앱 스토어 배포 가이드(Apple App Store, Google Play, Microsoft Store)는 Tauri 2.0이 공식 문서로 제공하고, Electron도 auto-update 체계가 오래 검증됐습니다.

### Node 의존 코드의 이관

가장 현실적인 비용은 여기입니다. Electron 메인 프로세스의 Node.js 코드는 Tauri에서 Rust 커맨드로 다시 써야 합니다. 예를 들어 Electron의 IPC 핸들러는

```js
// Electron 메인 프로세스 — Node.js API를 그대로 쓸 수 있음
const { app, BrowserWindow, ipcMain } = require("electron");
const fs = require("node:fs/promises");

app.whenReady().then(() => {
  const win = new BrowserWindow({
    webPreferences: { contextIsolation: true, preload: "preload.js" },
  });
  win.loadFile("index.html");
});

ipcMain.handle("read-config", () => fs.readFile("config.json", "utf8"));
```

같은 기능을 Tauri에서는 Rust로 옮기고 프론트엔드에서 `invoke`로 호출합니다.

```rust
use std::fs;
use tauri::command;

#[command]
fn read_config() -> Result<String, String> {
    fs::read_to_string("config.json").map_err(|e| e.to_string())
}

fn main() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![read_config])
        .run(tauri::generate_context!())
        .expect("Tauri 앱 실행 실패");
}
```

```ts
// 프론트엔드 — Rust 커맨드 호출
import { invoke } from "@tauri-apps/api/core";

const config: string = await invoke("read_config");
```

`fs.readFile` 한 줄짜리야 금방이지만, Node 스트림·워커·기존 npm 래퍼 라이브러리에 얽힌 코드가 많다면 이관은 "재작성 프로젝트"가 됩니다. 공식 [마이그레이션 가이드](https://v2.tauri.app/start/migrate/from-tauri-1/)와 `tauri migrate` CLI가 도와주는 대상도 Tauri 1.x → 2.0이지 Electron → Tauri가 아닙니다. Rust 학습 비용을 포함해 2~4주 단위의 학습 곡선을 잡는 것이 현실적입니다.

## Electron이 여전히 이기는 지점

공정한 비교를 위해 Electron의 우위를 명확히 하겠습니다.

1. **브라우저 버전 일관성**: 앱이 Chromium을 번들하므로 OS·시스템 WebView 상태와 무관하게 동일한 렌더링이 보장됩니다. Tauri는 WebKitGTK(Linux)와 WebView2/WebKit 사이의 차이를 테스트해야 합니다. Tauri 로드맵에 Linux 대안(CEF)과 Servo 실험이 올라 있긴 하지만, 이 글을 쓰는 시점엔 디폴트가 아닙니다.
2. **Node.js API 전체**: 메인 프로세스가 Node 그 자체라 npm 생태계와 네이티브 모듈을 제약 없이 쓸 수 있습니다.
3. **검증된 지원 정책**: [Electron은 최신 3개 메이저 버전을 지원](https://www.electronjs.org/docs/latest/tutorial/electron-timelines)하며 Chromium 릴리스 주기에 맞춰 보안 패치가 흘러갑니다. 조직 배포에서 "지원 윈도"가 명확하다는 것은 실제로 큰 자산입니다.
4. **레퍼런스와 사례**: 10년 가까운 생태계라 트러블슈팅 검색 히트율이 다릅니다.

## 선택 기준 체크리스트

다음 항목에 하나라도 해당하면 **Electron**이 무난합니다.

- 메인 프로세스 로직이 Node.js/npm 의존도가 높다 (파일 스트림, 기존 npm 래퍼 등)
- 모든 머신에서 동일한 Chromium 렌더링이 요구된다 (예: 복잡한 그래픽 도구)
- 팀에 Rust 경험이 없고 학습 여유가 없다
- 조직 정책상 "지원되는 최신 3버전" 같은 명시적 지원 윈도가 필요하다

다음 항목에 해당하면 **Tauri 2.0**이 유리합니다.

- 설치 크기·다운로드 비용이 제품 경쟁력에 직결된다 (유틸리티, CLI 동반 도구)
- iOS/Android까지 겨냥한 단일 UI 코드베이스가 전략이다
- 코어 로직이 가볍고(설정 읽기, 얇은 래퍼) Rust로 옮길 분량이 적다
- 권한 최소화·보안 감사 서류가 납품 요건이다

둘 다 해당하지 않는다면, 저는 "프론트엔드 자산은 어차피 공유되니 소규모 파일럿을 각각 1주일씩 만들어 보고 결정하라"를 권합니다. 아키텍처 차이는 읽는 것보다 직접 부딪히는 쪽이 훨씬 빨리 체감됩니다.

## 마무리

Tauri 2.0은 "Chromium을 배송하지 않는 Electron 대안"이라는 초기 약속을 모바일 지원과 capability 기반 보안으로 확장하며 완성도를 높였고, Electron은 여전히 일관성과 생태계라는 확실한 우위를 지킵니다. 프레임워크의 우열이 아니라, 배포 크기·브라우저 일관성·기존 자산이라는 세 변수에서 내 앱이 무엇을 감당할 수 있는지가 선택의 본질입니다. 이 비교가 결정 문서의 초안이 되기를 바랍니다.

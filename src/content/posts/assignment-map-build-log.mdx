# AI 과제 지도(assignment-map) 구축기 — 수집기 흰 화면 복구부터 18종 레퍼런스 기반 UI 개편까지

채용 사전 과제, 해커톤, 공모전에서 가장 먼저 확인해야 하는 건 두 가지입니다. **마감이 언제인가**, 그리고 **AI를 써도 되는가**. 두 번째가 특히 애매합니다. 어떤 공고는 "AI 활용을 적극 권장합니다"라고 쓰고, 어떤 공고는 전형 안내 세 번째 문단에 "AI 생성물 제출 시 불이익"이라고만 적습니다. 사람이 매일 열 개 사이트를 돌면서 이 문장을 찾는 건 오래 못 갑니다.

그래서 만든 것이 **과제 지도(assignment-map)** 입니다. 매일 03:00 KST에 국내외 채용 과제·해커톤·대회·공모전·밋업을 수집해서, AI로 만들어 제출할 수 있는 기회만 근거 문장과 함께 공개하는 데이터 리포 + 정적 사이트입니다.

- 사이트: [developjik.github.io/assignment-map](https://developjik.github.io/assignment-map/)
- 데이터: `data/*.json` (RSS·JSON Feed 발행)
- 비용: ₩0 — GitHub Actions + Pages 무료 쿼터만 씁니다. 외부 DB도, 서버도 없습니다.

이 글은 2026-11-12부터 11-17까지 6일 동안 올린 **PR 16건** 중에서, 다시 봐도 값이 있는 네 지점을 기록으로 남깁니다. ① 왜 이 구조인가 ② 데이터 하나가 화면을 죽인 장애 ③ 18종 레퍼런스를 재고 다섯 개 PR로 나눈 UI 개편 ④ `npm ci`보다 먼저 도는 테스트가 배포를 막은 CI 함정입니다.

## 1. 무엇을 추적하는가

| 유형 | 판별 기준 |
| --- | --- |
| 채용 과제 | 상세 본문의 전형 절차에 사전 과제가 있고, AI 정책 문구가 있는 공고 |
| 해커톤 | 주제·상금·채용 연계가 있는 국내외 AI 해커톤 |
| 대회 | AI 활용 정책이 명시된 경진대회·챌린지 |
| 공모전 | 제출물에 AI 사용 가능 여부가 있는 공모 |
| 밋업 | 개발자 대상 세미나·컨퍼런스·워크숍 |

2026-11-17 기준 숫자입니다. 이 표는 사람이 고치지 않습니다. 배포마다 `scripts/sync-readme.mjs`가 `data/*.json` 실측으로 다시 씁니다.

| 항목 | 값 |
| --- | --- |
| 추적 레코드 | 210건 (채용 공고 54 · 이벤트 156) |
| 지금 열려 있는 기회 | 104건 (채용 공고 33 · 이벤트 71) |
| AI 정책을 명시한 진행중 항목 | 75건 (그중 AI 필수 62건) |
| 피드 발행 항목 | 104건 (RSS 2.0 + JSON Feed 동일 목록) |
| 골든케이스 | 6/6 (정책 판정 회귀 방지) |
| 안티-슬롭 검사 | 16체크, 실패하면 빌드 중단 |

설계에서 먼저 정한 규칙은 세 가지였습니다.

1. **원문이 아니라 근거 한 문장만 남긴다.** 레코드는 `evidence`(인용 문장)와 `last_checked`(확인일)를 1급 필드로 갖습니다. 정책은 광고 문구가 아니라 원문에서만 판정하고, 원문 전문은 저장하지 않습니다. 저작권도 그렇고, 저장하는 순간 갱신 책임이 끝없이 늘어납니다.
2. **AI를 금지하는 기회는 기록만 하고 화면에서 뺀다.** 이 지도의 목적이 "AI로 만든 결과물 → 포트폴리오·채용"이라, 금지 대회는 사용자에게 노이즈입니다. 데이터에는 `ai_usage: banned`으로 남습니다.
3. **수집이 사람 손을 타지 않게 한다.** 수집은 fetch 우선입니다. JSON·RSS·SSR 페이지는 HTTP로 긁고, 브라우저는 JS 렌더가 필요한 상세와 재방문에만 씁니다. 브라우저 페이지 상한에 묶이지 않으려는 선택입니다.

```
03:00 KST  수집 (신규 스캔 + active 재방문 큐)
   ↓
merge.mjs      신규·변경·종결 diff, history 누적
   ↓
validate.mjs   스키마 무결성 + 골든케이스 6/6 → 실패하면 커밋 잠금
   ↓
Actions        slop-lint 16체크 → rollup + terser → feed.xml / feed.json / sitemap
   ↓
Pages 배포     watchdog가 26시간 무갱신이면 이슈로 경보
```

웹은 React 18 + Rollup 3입니다. 빌드 타임에 `data/*.json`을 번들에 넣으므로 런타임 API 호출이 없고, 그래서 운영비가 계속 0입니다. 대신 **데이터가 곧 프런트엔드 코드**라는 성질을 갖습니다. 이 성질이 다음 장의 사고를 만들었습니다.

## 2. 흰 화면 — evidence가 문자열로 들어온 날

2026-11-16 08:26 KST, 배포된 사이트가 흰 화면이었습니다. 콘솔에는 이런 오류가 있었습니다.

```text
TypeError: (p.evidence || []).map is not a function
```

원인은 그날 새벽 03:17 수집 커밋(`8d28ab3`)이었습니다. 잡코리아에서 가져온 공고 5건의 `evidence`가 배열이 아니라 **문자열 하나**로 들어갔습니다.

```jsonc
// 정상: postings의 evidence는 quote 객체 배열
"evidence": [{ "quote": "서류전형 > 사전과제 > 면접", "field": "전형" }]

// 사고: jobkorea:50283588 — 문자열 하나
"evidence": "잡코리아 GI_Read 브라우저 실측(2026-11-16): '마감되었습니다' 표시 — SOOP LIVE 방송 서버 개발, 마감일 11-15 경과"
```

`data.js`는 `evidence`를 `(p.evidence || []).map(...)`으로 펼쳐서 검색 인덱스와 패널용 인용 목록을 만듭니다. 문자열에는 `.map`이 없으니 모듈 평가 단계에서 던지고, **빌드 타임 번들이라 레코드 하나의 예외가 목록 전체를 죽입니다.** 레코드 206건 중 5건의 필드 하나가, 그 화면을 통째로 흰색으로 만들었습니다.

### 1차 대응: 화면에서 먼저 버티게 (PR #7)

먼저 배포를 살렸습니다. 데이터는 그대로 두고 읽는 쪽을 관대하게 만들었습니다.

```js
// 수집기가 evidence 를 문자열로 남긴 행이 있다(2026-11-16 잡코리아 5건). 배열로 맞춰 준다.
// 문자열에 .map 을 부르면 목록 전체가 죽는다(흰 화면).
const asEvidence = (ev) => (Array.isArray(ev) ? ev : ev ? [{ quote: String(ev) }] : [])
```

핸드오프 시점에 확인해서 PR을 올리고, 머지 직후 흰 화면은 복구됐습니다. 하지만 이건 응급처치입니다. 화면이 관대해지면 **다음에도 조용히 틀린 데이터가 들어옵니다.** 그 데이터를 세는 모든 곳(패널, 피드, 검색 인덱스, 쇼츠 대본)이 각자 방어해야 하니까요.

### 뿌리 수정: 저장 전에 막고, 검증에서 잠근다 (PR #8)

두 번째 PR은 규칙을 한 파일로 모으고, 세 지점에서 같은 규칙을 강제했습니다.

| 지점 | 역할 |
| --- | --- |
| `collector/merge.mjs` | 저장 **전** 정규화. 새 레코드도, 기존 레코드에 남은 문자열도 병합할 때 배열로 정리(멱등) |
| `collector/normalize.mjs` | 이미 들어간 `data/*.json`을 정리. `--check`는 고칠 게 남아 있을 때만 exit 1 |
| `collector/validate.mjs` | 검증. 문자열 evidence면 `VALIDATE FAIL` + exit 1 → **커밋 잠금** |

`collector/evidence.mjs`가 그 규칙의 본체입니다.

```js
export function asEvidence(value, { quoteObjects = false } = {}) {
  const list = Array.isArray(value) ? value : value === undefined || value === null ? [] : [value];
  const out = [];
  for (const item of list) {
    if (typeof item === 'string') {
      const quote = item.trim();
      if (quote) out.push(quoteObjects ? { quote } : quote);
      continue;
    }
    if (!isQuoteObject(item)) continue;   // 숫자·불리언·빈 객체는 근거가 아니다
    const quote = item.quote.trim();
    if (!quote) continue;
    out.push(quoteObjects ? { ...item, quote } : quote);
  }
  return out;
}
```

검증은 "배열인가"에서 끝내지 않았습니다. 원소까지 봅니다. `postings`의 evidence는 원래 `{ quote, field }` 객체이고(패널이 `field`로 "정책/전형/리서치"를 구분합니다), `events`는 문자열 배열이기 때문입니다.

```js
export function evidenceProblem(value) {
  if (!Array.isArray(value)) {
    const what = value === undefined ? '없음' : value === null ? 'null' : typeof value;
    return `evidence 가 배열이 아니다 (${what})`;
  }
  for (const [i, item] of value.entries()) {
    if (typeof item === 'string') {
      if (!item.trim()) return `evidence[${i}] 가 빈 문자열`;
      continue;
    }
    if (isQuoteObject(item)) {
      if (!item.quote.trim()) return `evidence[${i}].quote 가 빈 문자열`;
      continue;
    }
    return `evidence[${i}] 가 문자열도 quote 객체도 아니다`;
  }
  return null;
}
```

이 과정에서 드러난 사실 하나가 더 있습니다. **이벤트 152건의 evidence도 필드 자체가 문자열 하나**였습니다. 스키마상 이벤트의 evidence는 문자열 배열이니, 검증을 켜는 순간 152건이 한꺼번에 걸립니다. 그래서 정리 도구를 먼저 돌려 배열로 바꾸고 검증을 통과시켰습니다. 검증을 켜면 그동안 아무도 보지 않던 위반이 한꺼번에 드러납니다 — 이건 검증이 늦었다는 뜻이고, 동시에 이제는 드러난다는 뜻입니다.

같은 PR에서 뉴스 수집기(`fetch_news.py`)도 멱등하게 고쳤습니다. 기사 id를 URL 해시로 바꾸고, 결과가 지금 파일과 같으면 쓰지 않습니다. 이전에는 회차마다 `01, 02…`로 밀려서 파일 전체가 diff가 됐습니다.

검증 결과입니다.

```text
node collector/validate.mjs           VALIDATE OK — 골든케이스 6/6 · postings 54 · events 152
node collector/normalize.mjs --check  NORMALIZE CHECK OK — 정규화할 필드 없음
node --test collector/tests/          pass 8 / fail 0  (문자열 evidence → 배열, 문자열 evidence → validate 실패)
python3 -m unittest discover -s collector/tests        5 tests OK
cd web && npm run build               BUILD OK — feed 104 items
```

### 조용한 실패는 더 비싸다 (PR #10)

흰 화면은 시끄러운 실패였습니다. 반대로 값싸게 끝나는 실패는 3주 동안 다섯 번 파서를 부쉈습니다(잡코리아 m ×3, 위비티 SSR, hide-dday). 전부 **에러 없이 빈 결과**를 내는 실패였습니다.

- 파서를 `collector/parsers/`에 영구 스크립트로 내리고(stdin → stdout 순수 함수 5종), 실응답 6종을 fixture로 고정했습니다. 사고가 나면 **fixture 갱신 → 케이스 추가 → 파서 수정** 순서로 "사고를 테스트로" 바꿉니다.
- `canaries.json`에 지표 7개의 정상 밴드를 두고, `canary.mjs`가 밴드를 벗어나면 exit 1로 멈춥니다. 빈 결과가 정상인지 아닌지는 파서가 아니라 **기대치**가 판단해야 하니까요.

정리하면 이 장의 교훈은 세 줄입니다.

- 화면에서 막는 것과 데이터가 틀려 들어오는 것을 막는 것은 다르다.
- 검증은 **커밋 앞**에 있어야 하고, 실패하면 데이터가 아니라 커밋을 잠가야 한다.
- 시끄러운 실패보다 조용한 실패를 먼저 의심한다.

## 3. 18종 레퍼런스 → 다섯 개 PR (PR #11~#15)

11-17 UI 개편은 취향에서 시작하지 않았습니다. 먼저 **결정해야 할 세 질문**을 적었습니다.

1. 필터·정렬 컨트롤 **20개**를 어떻게 계층화하는가
2. 리스트 행에서 무엇을 빼서 상세 패널로 보내는가
3. 2-Pane이 열렸을 때 표와 패널의 비율·컬럼은 어떻게 잡는가

그리고 그 질문에 답하는 제품 18종을 조사했습니다. 축 1(고밀도 테이블·인스펙터) 9종 — Linear, GitHub Issues, Datadog, Grafana, Vercel Runtime Logs, Raycast, k9s, Carbon/Polaris, NN/g. 축 2(기회 애그리게이터) 9종 — Devpost, Luma, Levels.fyi, Wellfound, YC, GeekNews, HN Jobs, Huntr, Contra/Peerlist.

조사 방법도 같이 남겼습니다. Devpost·Luma·GitHub·GeekNews·Levels.fyi·HN Jobs·Wellfound와 **배포 중인 과제 지도 자체**는 10:20~10:55 KST에 브라우저로 직접 열어 `getBoundingClientRect`로 값을 쟀고, 로그인 벽 뒤에 있는 Linear·Datadog·Grafana·Vercel·Raycast·k9s·Carbon은 **공식 문서 기반**이라고 표시했습니다. 확인하지 않은 배치는 쓰지 않았습니다. 이 구분이 없으면 "레퍼런스 조사"는 그럴듯한 추측 모음이 됩니다.

### 기준선: 다섯 개의 결함

| C (#13) | 2-Pane 폭·브레이크포인트·컬럼 재배분 | 패널 `clamp(340px, 30%, 480px)` → 1919px 73:27, 1440px 382px, 표 1,271px |
| D (#14) | 밀도 3단·wide 컬럼 토글·일괄 액션 바 | 행 높이 24 / 28 / 40px, 배치 바 31px |
| E (#15) | 마감 표기 D-1 단일화 | 마감 컬럼 92 → 72px, 네 곳에서 따로 적던 표기를 한 파일로 |

### A — 필터를 접을 때 같이 정한 것

팝오버의 값 한 줄이 곧 토글 한 줄입니다(체크박스 없음). 그리고 오른쪽 숫자는 **그 값을 골랐을 때 남는 건수**인데, 이 숫자를 셀 때 **자기 축의 조건은 빼고 셉니다**(Datadog facet 방식). 그래야 "지금 조합에서 0이 되는 길"이 누르기 전에 보입니다. 115건 중 `미언급/확인필요 0`이면 그 값은 막다른 길이라는 뜻이니까요.

프리셋 3종(D-3 임박 / AI 필수 / 관심)은 저장 뷰를 새로 만들지 않았습니다. 프리셋은 **정의만** `localStorage`에 두고, 적용은 언제나 지금의 필터 상태(=URL 해시)로 흘러갑니다. 그래서 프리셋을 눌러도 저장 뷰가 아니라 **링크**가 남습니다. 마감 범위를 해시 파라미터(`dd=3|7`)로 추가해 `#dd=3` 하나로 'D-3 임박'이 재현됩니다.

대비 수정도 판단이 하나 있었습니다. AA 미달인 `--faint`를 `--mut`(6.37:1)로 바꾸는 대신 **토큰 자체를 5.04:1로 올렸습니다.** 도구 줄·메타가 조건 버튼과 같은 밝기가 되면 "목록을 좁히는 조건"과 "표시 도구"의 위계가 사라지기 때문입니다. 되돌리기는 토큰 한 줄이면 되니, 판단이 걸리면 쉽게 원복할 수 있게 남겨 두었습니다.

### B — 한 필드에 세 가지가 섞여 있었다

수집기는 `evidence` 한 필드에 세 가지를 같이 남기고 있었습니다.

```text
GI_Read_Comt_Ifrm 본문(2026-11-07): '서류전형 > 사전과제 > 면접' — 사전과제 전형 명시. AI 정책 언급 없음
└ 출처 라벨(운영)                    └ 원문 인용             └ 수집가의 판단(운영)
```

사용자에게 필요한 건 가운데 한 조각입니다. `splitEvidence()`가 이 셋을 가르되, **데이터 파일은 건드리지 않고 표시 계층에서만** 가릅니다. 수집기가 남긴 원문은 그대로 보존해야 나중에 판단을 검증할 수 있으니까요.

결과: 진행중 115건 중 **109건**이 표에 원문 인용을 얻었고, **6건**은 인용 없이 운영 메모만 있어 근거 셀이 비었습니다. 이 6건은 예전에 "Devpost 오픈 목록 이탈 + 제출마감 경과 이중 확인" 같은 문장이 근거 자리에 있었습니다. **빈 칸이 잘못된 문장보다 정직합니다.** 메모는 패널의 접힌 "수집 메모"에 그대로 남습니다.

### C — 드로어 예외를 넣지 않은 이유

레퍼런스 조사안에는 "표가 660px 밑으로 내려가는 폭에서만 드로어를 예외로 허용"이 있었습니다. 구현 전에 계산해 보니 발동 조건이 없었습니다. 표 폭은 `본문폭 − max(340, 0.3 × 본문폭)`이고, 이 값이 660px 밑으로 내려가는 경계는 뷰포트 **1,168px** — 2-Pane이 켜지는 1200px보다 좁습니다. 1200·1280·1366·1440·1519·1520·1600·1919에서 표는 692~1,751px였습니다.

그래서 드로어는 넣지 않고, 대신 표에 `min-width: 660px`을 걸었습니다. 나중에 폭 계산이 바뀌어도 표가 찌그러지는 대신 자기 영역에서 스크롤하는 안전망입니다. **스펙에 있는 예외를 조건이 성립하지 않으면 넣지 않는 것**도 구현입니다.

컬럼 재배분은 규칙 하나로 끝냈습니다. 짧은 컬럼은 px로 못 박고(대상/주최 170 · 정책 96 · 마감 92), 근거는 표 폭의 28%, **제목이 남는 폭 전부**를 갖습니다. 이전엔 다섯 컬럼이 %로 균등 배분이라 1919px에서 마감이 189px, 정책이 149px를 쓰면서 제목이 405px에 묶여 있었습니다.

상단 밴드도 손봤습니다. 헤더 태그라인·티커 바·헤더에 세 번 적히던 수집 시각을 헤더 한 곳(`수집 2026-11-17 03:00`)으로 모아 **209px를 회수**했고, 그 폭이 마감 임박 티커로 갔습니다(1,032 → 1,241px).

### D — 밀도는 세 단, 저장값은 호환되게

| 밀도 | 행 높이(실측) | 구성 |
| --- | --- | --- |
| `compact` | 24px | 1줄. 근거 컬럼을 접어(폭 0) 제목이 그 폭을 갖는다 |
| `default` | 28px | 1줄 + 근거 48자 (기존 기본) |
| `comfortable` | 40px | 2줄: 제목 + `주최 \| 유형 \| 확인 10-27` |

세 단 모두 `getBoundingClientRect` 실측이 24.0 / 28.0 / 40.0px입니다. 28·24px는 아이콘·배지의 baseline 1px이 행을 밀어 29px·25px로 서던 것을 td 높이 고정과 별표 `vertical-align: middle`로 잡았습니다. 눈으로 맞춘 값이 아니라 잰 값입니다.

저장값은 이름이 바뀌어도 뜻이 유지되게 매핑했습니다. `standard → default`, `wide → comfortable`. 키는 `am-density` 하나 그대로라, 예전 값이 남은 브라우저에서도 사용자가 고른 뜻(훑기/기본/검토)이 유지됩니다. 모르는 값이나 저장소 예외는 `default`로 떨어집니다.

단축키 충돌도 정리했습니다. 선택 중에는 행 클릭이 선택 토글이 되고, **Esc는 패널보다 선택을 먼저 걷습니다**(한 번 = 선택 해제, 두 번째 = 패널 닫기). 단축키를 늘릴 때마다 "지금 이 키가 무엇을 하고 있는가"의 순서를 정해야 합니다.

### E — 같은 사실을 네 곳이 다르게 적고 있었다

마감 표기가 `D-0` / `D-DAY` / `D-0 오늘`처럼 표·패널·티커·관련 공고에서 조금씩 달랐습니다. `web/src/lib/deadline.js` 하나로 모으고, 행에는 상대값만 남겼습니다.

```js
export const HOT_DAYS = 3    // 긴급 창 — 이 안쪽만 red
export const NEAR_DAYS = 7   // 여기까지 본문색, 그 밖은 차분하게

export function relativeText(dd, open = true) {
  if (!open) return '종결'
  if (dd === null || dd === undefined) return '상시'
  if (dd < 0) return '마감'
  return dd === 0 ? 'D-Day' : 'D-' + dd
}
```

색은 임계값 하나로만 씁니다. `D-3` 이하(0~3일, D-Day)만 red, `D-4`~`D-7`은 본문색, `D-8` 이상·`상시`는 `--mut`, 지난 마감·`종결`은 `--faint`. **빨강은 긴급에만** 씁니다. 절대 날짜는 사라지지 않고 셀 `title`(`2026-11-18 마감 | D-1`), 상세 패널, 좁은 화면 아코디언으로 내려갔습니다. `D-` 접두사는 흐리게, 숫자는 굵게 — 같은 폭에서 숫자가 먼저 읽히게 했습니다(Levels.fyi의 단위 약화).

### 레퍼런스에서 가져오지 않은 것

조사 노트에 따로 적어 둔 목록입니다. **필(pill)·둥근 칩·카드 그리드·hover 부양·그림자**는 리포의 안티-슬롭 금지 목록과 정면 충돌합니다. **`middle-dot` 메타**는 Wellfound·Levels.fyi가 쓰지만 우리는 `|`를 씁니다. **상태 점의 남발**도 안 합니다 — Devpost는 상태에 점을 쓰지만 우리 색은 AI 정책 전용이고 상태는 글자입니다. **무한 스크롤**은 115건 규모에서 불필요합니다.

가져온 것은 배치와 위계, 그리고 검증 가능한 수치(행 높이, 패널 비율, 타깃 크기, 대비)뿐입니다. 레퍼런스는 모양의 출처가 아니라 **결정의 근거**로 씁니다.

## 4. CI 함정 — `npm ci`보다 먼저 도는 `npm test` (PR #16)

PR #13·#14·#15를 머지한 뒤 배포가 세 번 연속 실패했습니다. 마지막 성공은 #12(`30b780f`)였습니다. 실패 로그는 이랬습니다.

```text
# tests 45
# pass 44
# fail 1
not ok 7 - web/tests/freshness.test.mjs
```

`deploy.yml`의 build 잡 순서가 원인이었습니다.

```yaml
- name: Collector + shorts 테스트 (파서 fixture 회귀 포함)
  run: npm test          # ← 여기, web/node_modules 가 아직 없다
- name: Install
  run: npm ci
  working-directory: web
```

PR #13이 추가한 `freshness.test.mjs`는 `web/src/lib/freshness.js`를 import하는데, 그 파일이 `import { useEffect, useState } from 'react'`를 포함합니다. `npm ci` 전이니 `react`가 없고, `ERR_MODULE_NOT_FOUND: Cannot find package 'react'`로 테스트가 죽습니다. 테스트가 실패하면 빌드가 멈추고 배포가 멈춥니다.

**로컬에서 안 보인 이유**는 단순합니다. 로컬에는 `web/node_modules`가 이미 있었습니다. 그래서 PR마다 `npm test`를 돌려도 초록이었습니다. CI 조건을 재현하려면 `web/node_modules`를 `web/node_modules.bak`으로 옮긴 상태에서 테스트를 돌려야 했습니다. 수정 후 검증도 그 조건에서 했습니다.

수정은 두 줄짜리 분리였습니다.

| 파일 | 내용 |
| --- | --- |
| `web/src/lib/freshnessDate.js` (신규) | `kstToday`·`daysSince`·`staleness`·`nextRun` — 날짜 계산만, React 의존 없음 |
| `web/src/lib/freshness.js` | `useStaleness` 훅만 남기고 날짜 계산은 `freshnessDate.js`에서 가져옴 |
| `web/tests/freshness.test.mjs` | import를 `freshnessDate.js`로 변경 |

### 재발 가드 — 규칙을 테스트로 박제한다

분리만 하면 다음에 누가 다시 훅 파일을 테스트에서 import합니다. 그래서 가드를 하나 더 넣었습니다. 테스트 파일에서 출발해 **상대 import를 따라가며**, `node:` 내장 모듈 밖의 bare specifier(=npm 패키지)가 하나라도 나오면 실패합니다.

```js
// deploy 워크플로는 web/node_modules 설치(npm ci) 전에 루트에서 `npm test` 를 돌린다.
// 그래서 테스트가 import 하는 모듈은 react 같은 패키지를 끌어오면 안 된다
// (PR #13 이후 freshness.test.mjs → freshness.js → 'react' 로 deploy 가 연속 실패했다).
function bareImportsOf(file, seen = new Set(), chain = [file]) {
  if (seen.has(file)) return []
  seen.add(file)
  const found = []
  for (const spec of specifiersOf(file)) {
    if (spec.startsWith('node:')) continue
    if (!spec.startsWith('.')) {
      found.push({ spec, chain: [...chain, spec] })
      continue
    }
    const target = resolveRelative(file, spec)
    assert.ok(target, `풀리지 않는 import: ${chain.join(' → ')} → ${spec}`)
    found.push(...bareImportsOf(target, seen, [...chain, target]))
  }
  return found
}
```

가드는 **일부러 실패시켜서** 확인했습니다. `freshness.test.mjs`의 import를 잠시 `freshness.js`로 되돌리면 `react ← … → freshness.js → react`로 실패하고, 원복하면 통과합니다. 통과만 확인한 가드는 가드가 아닙니다.

검증은 CI와 같은 조건에서 이렇게 나왔습니다.

```text
npm test (루트, node_modules 없음)   exit 0, 47 pass / 0 fail (가드 포함)
npm run lint:slop                    SLOP-LINT OK — 16체크 (38개 파일)
npm run build                        BUILD OK — app.js 845.8KB (terser)
```

머지 후 `main`의 deploy는 초록으로 돌아왔습니다. 이 장의 교훈은 한 줄입니다. **테스트가 무엇을 import하는지가 CI 계약이다.** 테스트가 "내 코드가 맞다"만 검증하고 "CI 환경에서 돌 수 있다"를 검증하지 않으면, 로컬 초록은 아무것도 보장하지 않습니다.

## 5. 남긴 판단과 다음 후보

일부러 정하지 않고 남긴 것들입니다. 결정을 미루는 것도 기록해 두면 다음에 다시 계산하지 않습니다.

- **1320~1439px에서 wide 컬럼을 켜면** 표가 800px를 넘겨 근거가 남고 제목이 215~275px로 좁아집니다. 그 구간까지 근거를 접는 편이 나은지는 취향이라 그대로 뒀습니다.

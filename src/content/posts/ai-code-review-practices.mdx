# AI 코드 리뷰 실무

## 개요

팀에 AI 코드 리뷰가 들어온 지 1년쯤 됐습니다. 처음엔 "리뷰어가 필요 없어지나" 싶었는데, 결론은 다른 곳에 닿았습니다. AI 리뷰는 필터이고, 사람 리뷰는 판단이라는 역할 분리입니다. 그 과정에서 정리한 실무 노하우를 공유합니다.

## 무엇을 맡기고 무엇을 직접 볼까

저희 팀의 기준은 이렇습니다.

**AI에게 맡기는 것**

- 반복 가능한 기계적 검사: 미사용 변수, 닫히지 않은 리소스, 일관되지 않은 에러 처리
- 보안 패턴 체크: 위험한 innerHTML 사용, 하드코딩된 시크릿, 쿼리 직접 연결
- 명시적 규칙 위반: 팀 컨벤션 문서에 적힌 항목

**사람이 직접 보는 것**

- 설계의 적절성: 이 추상화가 필요한가, 경계는 올바른가
- 도메인 정확성: 비즈니스 규칙을 코드가 제대로 반영했는가
- 팀 맥락: 이 변경이 다른 팀·시스템에 미치는 영향

AI는 diff를 보고, 사람은 그 diff가 놓인 맥락을 봅니다.

## 오탐 대응

AI 리뷰의 최대 적은 오탐입니다. 오탐이 쌓이면 "AI 코멘트는 대충 무시하는" 습관이 생기고, 그 순간 진짜 잡아야 할 것도 놓칩니다. 저희가 쓴 대응은 세 가지입니다.

1. **무시 기준을 문서화한다**: "타입 단순화 제안은 이미 검토된 패턴이므로 반려"처럼 팀 합의를 문서로 남깁니다
2. **규칙 파일로 조율한다**: 오탐이 반복되면 프로젝트의 AI 규칙 파일에 제외 항목을 추가합니다

```markdown
# review-guidelines.md (AI 규칙 파일)

- 테스트 파일의 any 허용 (픽스처 용도)
- storybook 스토어의 구조 분해 제안 금지
- 에러 처리는 Result 패턴 사용, try-catch 제안 금지
```

3. **오탐율을 가끔 샘플링한다**: 코멘트 20개를 골라 진짜/오탐을 세어봅니다. 숫자를 보면 규칙 파일 수정이 필요한 타이밍이 보입니다.

## 리뷰 품질 기준

AI 코멘트든 사람 코멘트든, 리뷰 품질의 기준은 같다고 봅니다.

- 근거가 있는가: "왜"가 한 문장이라도 붙는가
- 실행 가능한가: 제안이 구체적으로 무엇을 하라는 것인가
- 우선순위가 있는가: 치명적 문제와 취향 차이가 구분되는가

저희는 AI 리뷰 설정에서 스타일류 코멘트를 끄고, 보안·버그 가능성·명시적 규칙 위반만 남겼습니다. 코멘트 수는 줄었지만 채택률은 올라갔습니다.

## 마무리

AI 코드 리뷰는 리뷰어를 대체하지 않았지만, 리뷰의 하한을 올렸습니다. 기계적 검사를 AI에 넘기고 사람은 설계와 도메인에 집중하는 분업. 그리고 오탐을 방치하지 않고 규칙으로 조율하는 운영 노력이 실무의 핵심이었습니다.

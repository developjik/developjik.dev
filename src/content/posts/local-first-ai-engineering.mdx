# 클라우드 서버 없이 브라우저가 로컬 Rust 데몬과 직접 대화하는 이유 — local-first AI 엔지니어링 원칙 3가지

**시리즈** · 1편 (이 글) · 2편 [왜 코드·스펙 에이전트에서 임베딩과 벡터DB를 버렸는가](/posts/why-not-embeddings)

AI 기능을 붙인 제품을 만들다 보면 결국 세 가지 결정으로 수렴한다. **진실의 원천을 어디에 둘 것인가. 상태를 누가 소유할 것인가. 품질을 무엇으로 판정할 것인가.**

업계의 기본값은 정해져 있다. 벡터 데이터베이스에 임베딩을 넣고, 클라우드 오케스트레이터가 세션을 들고, 리뷰는 "잘 동작하는 것 같다"로 끝난다. 나는 Damon, spec-studio, sqlite-graph-mcp를 만들면서 세 번 다 반대쪽을 골랐다. 이 글은 그 선택이 왜 필요했는지, 무엇을 포기했는지, 어떤 숫자로 그것을 지키고 있는지의 기록이다. 일반론은 쓰지 않는다. 코드에 남은 제약과 다시 돌려서 나온 측정값만 쓴다.

> **세 원칙**
>
> 1. 단일 진실 원천은 로컬에 둔다 — 임베딩 대신 결정적 그래프, 그리고 모든 답에 `file:line`.
> 2. 데몬 하나, 표면은 얇게 — 세션·권한·히스토리는 상주 데몬이 소유하고 클라이언트는 같은 프로토콜의 얇은 껍데기다.
> 3. 증거 없는 자동화는 자동화가 아니다 — 품질을 골든케이스, 불변식, 발화 계측 같은 테스트 가능한 계약으로 바꾼다.

세 제품은 공통 제약을 하나 공유한다. 서버를 운영하지 않고(운영비 0원), 사용자 계정을 만들지 않고, 혼자 만든다. 이 제약이 아래 선택의 상당 부분을 강제했다. 제약을 먼저 밝히는 이유는, 이 글이 "이게 정답"이 아니라 "이 조건에서 이것이 남았다"는 기록이기 때문이다.

---

## 1. 먼저, 실패가 조용하다는 것

세 장면이 있다. 셋 다 예외가 나지 않는다.

**코드 구조 질문.** "`walkGraph`를 쓰는 파일이 어디야?" 임베딩 검색은 비슷하게 생긴 청크 다섯 개를 준다. 두 개는 실제 사용처고 세 개는 이름만 비슷한 다른 함수다. 어느 것도 `file:line`을 주지 않는다. 모델은 그럴듯하게 요약하고, 나는 다시 grep을 친다. 검색이 답을 준 게 아니라 후보를 준 것이다.

**화면 기획서.** 핀 #3을 지우고 #4를 #3으로 당긴다. 지난주 리뷰 코멘트 "SCR-110-3의 예외 처리"는 이제 다른 요소를 가리킨다. 틀렸다는 신호는 어디에도 없다. 문서는 조용히 거짓말이 된다.

**스트리밍 채팅 UI.** 토큰이 도착할 때마다 `aria-live` 영역을 다시 쓰면, 스크린리더는 반 단어씩 끊어 읽다가 답이 끝났다는 사실은 말해주지 않는다. DOM은 정상이고, 클릭 스크립트 테스트는 통과한다. 사용자만 막힌다.

공통점은 셋 다 로그도, 실패도 남기지 않는다는 것이다. 그래서 **"동작한다"와 "증명된다" 사이에 간격**이 생기고, 그 간격은 리뷰어의 시간으로 메워진다. 아래 세 원칙은 이 간격을 데이터, 상태, 품질이라는 서로 다른 층에서 없앤다.

## 2. 원칙 1 — 단일 진실 원천은 로컬에 둔다

### 2.1 임베딩 대신 그래프: sqlite-graph-mcp

임베딩 파이프라인이 구조 질문에 답하지 못하는 이유는 세 가지다.

- **결정적이지 않다.** 같은 코드, 다른 인덱스, 다른 청크, 다른 답. 회귀 테스트를 만들 수 없다.
- **청크 경계가 구조를 자른다.** import 관계는 파일과 심볼 사이의 간선인데, 청크는 그 경계를 임의로 자른다.
- **답에 좌표가 없다.** "관련 있어 보이는 텍스트"는 근거가 아니다. 검증 비용이 답을 만든 비용보다 크다.

그래서 인덱스 시점에 그래프를 확정하고, 질문은 SQL로 답하기로 했다. 노드는 4종(`file`, `symbol`, `heading`, `package`), 간선은 6종(`imports`, `exports`, `defines`, `links_to`, `depends_on`, `references`)이다. 스키마 자체가 인용을 강제한다.

```sql
CREATE TABLE edges (
  id   INTEGER PRIMARY KEY AUTOINCREMENT,
  src  INTEGER NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  dst  INTEGER NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  type TEXT NOT NULL CHECK (type IN ('imports','exports','defines',
                                     'links_to','depends_on','references')),
  line INTEGER,
  meta TEXT NOT NULL DEFAULT '{}',
  UNIQUE (src, dst, type)
);
```

노드는 `path`와 `line`을 들고 있고, 간선은 그 관계가 만들어진 줄 번호를 들고 있다. `toNodeView`가 그 두 값으로 `citation`을 만든다. **인용은 기능이 아니라 스키마의 결과다.** citation이 null인 경우는 매니페스트에 없는 외부 패키지 노드 하나뿐이고, 그건 파일이 아니라 의존성 이름이라 좌표가 있을 수 없다.

순회는 재귀 CTE 하나다. 사이클 차단을 visited 테이블이 아니라 경로 문자열로 한 이유는, 재귀 CTE 안에서 추가 상태를 들고 다니지 않기 위해서다.

```sql
WITH RECURSIVE walk(id, depth, path) AS (
  SELECT id, 0, ',' || id || ',' FROM nodes WHERE id IN (?, ?)
  UNION ALL
  SELECT e.dst, w.depth + 1, w.path || e.dst || ','
  FROM walk w
  JOIN edges e ON e.src = w.id
  WHERE w.depth < :maxDepth
    AND instr(w.path, ',' || e.dst || ',') = 0
    AND e.type IN ('imports', 'links_to')
)
SELECT id, MIN(depth) AS depth FROM walk GROUP BY id ORDER BY depth, id;
```

`a → b → a`는 `maxDepth`가 20이어도 깊이 1에서 끝난다. `UNION ALL`에 `instr` 조건 하나 붙인 것이 전부다.

연산자는 다섯 개다. `find`(FTS5 prefix 랭킹 + substring/glob 폴백), `walk`(방향·깊이·간선 타입), `filter`(kind/path/prefix/name/regex/tag), `minus`(집합 차집합), `answer`(파이프라인 실행 + 인용 묶음). 중요한 건 연산자 수가 아니라 **모델이 하는 일이 바뀐다**는 점이다. 의미 검색에서는 모델이 검색기다. 무엇이 나올지 모르고, 나온 것을 요약한다. 플랜 실행에서는 모델이 쿼리 작성자다.

```
find "walker" kind=symbol | walk type=defines dir=in depth=1 | filter kind=file
→ file:src/graph/walker.ts · citation: src/graph/walker.ts:1
```

모델이 파이프라인을 쓰고, 엔진이 결정적으로 답한다. 같은 질문에 같은 답이 나오고, 답에는 항상 좌표가 붙는다.

인덱스는 한 트랜잭션에서 통째로 다시 만든다. 중간에 실패하면 이전 인덱스가 그대로 남는다. `journal_mode = WAL`, `foreign_keys = ON`, `synchronous = NORMAL`. 결과물은 `.sqlite-graph/index.db` 파일 하나이고 `.gitignore`에 넣을 수 있다. `sqlite3`로 열어서 에이전트의 추론을 직접 검사할 수 있다. **감사 가능성은 기능이 아니라 파일 형식의 성질**이다.

여기에 타협이 하나 있다. **의미 검색이 없다.** "이 함수가 무슨 일을 하는지"를 자연어로 물으면 못 찾는다. `find`가 FTS5 prefix와 substring/glob으로 버티는 게 전부다. 그래서 이 도구는 코드 검색기가 아니라 구조 질문기다. 그 경계를 넘는 질문은 모델이 파일을 읽어야 하고, 그때도 답의 근거는 `file:line`이어야 한다.

리뷰 게이트로도 쓴다. `graph_diff`는 두 리비전의 그래프를 비교해서, head에서 더 이상 export되지 않는 심볼을 **그걸 쓰던 파일의 인용과 함께** 낸다. `--check`는 breaking이 하나라도 있으면 exit 3으로 끝난다. "이 PR 머지해도 되나"를 사람의 기억이 아니라 그래프 차분으로 답하는 것이다.

### 2.2 같은 원칙을 문서에: spec-studio

한국어 화면 기획서는 이미 정확한 문법을 갖고 있다. 모든 요소에 번호가 붙고, 노트가 그 번호를 인용하고, 상태·권한·예외가 번호에 매달린다. 문제는 그 문법이 문서 편집기 안에서 지켜지지 않는다는 것이다. spec-studio는 그 문법을 객체로 바꿨다. 6개 객체(화면·핀·요구사항·정책·계약·QA)와 7개 링크(`implements`, `governs`, `handles_edge`, `verifies`, `references`, `derived_from`, `blocks`)다.

결정은 네 개다.

**1) 번호는 불변.** `pinSeq`는 화면 props에 단조 증가로 남고, 다음 핀은 `pinSeq + 1`이다. 삭제는 결번으로 남고 재사용하지 않는다. 번호를 재정렬하면 지난 리뷰 코멘트가 조용히 다른 요소를 가리키게 되기 때문이다. 이건 취향이 아니라 참조 무결성 문제다.

**2) 링크의 종류가 곧 계약.** 링크 타입마다 허용되는 src/dst kind가 정해져 있고, 그 계약은 애플리케이션이 아니라 SQLite 트리거가 강제한다.

```sql
CREATE TRIGGER link_kind_guard_ins BEFORE INSERT ON link FOR EACH ROW
WHEN NOT EXISTS (
  SELECT 1 FROM link_type lt, obj s, obj d
  WHERE lt.id = NEW.type AND s.id = NEW.src AND d.id = NEW.dst
    AND EXISTS (SELECT 1 FROM json_each(lt.src_kinds) WHERE json_each.value = s.kind)
    AND EXISTS (SELECT 1 FROM json_each(lt.dst_kinds) WHERE json_each.value = d.kind)
)
BEGIN
  SELECT RAISE(ABORT, 'link_kind_mismatch');
END;
```

"리뷰에서 잡자"는 규율은 6개월 뒤에 사라지지만 CHECK는 남는다.

**3) 인용은 원문.** `citation.quote`는 NOT NULL이고 길이 0을 허용하지 않는다. 요약이 아니라 복사만 들어간다. 근거를 요약할 수 있게 두면, 요약이 원문에서 멀어진 순간을 아무도 모른다.

**4) 되돌리기는 관습이 아니라 스키마.** 모든 쓰기는 `op_log`에 행을 남기고, 되돌릴 수 있어야 하는 변경 — `block.update`, `block.delete`, `proposal.adopt` — 은 before 없이는 INSERT 자체가 거부된다.

```sql
CHECK (kind NOT IN ('block.update','block.delete','proposal.adopt')
       OR before IS NOT NULL)
```

"실행 취소"가 기능 목록에 있는 것과, 취소할 수 없는 변경이 저장될 수 없는 것은 다르다.

번호는 불변이지만 문장의 의미는 변한다. 이 둘을 분리하는 데 해시를 쓴다. 핀의 type/title/body가 바뀌면 그 핀을 인용한 문단의 링크가 `suspect`가 되고, 이유와 리비전이 함께 남는다. 반면 위치 이동은 `suspect`를 만들지 않는다. 문장이 주장하는 것은 위치가 아니기 때문이다. 사람이 확인해 기준선을 다시 잡거나(`확인 · 해제`), 제안이 문장을 고친다.

여기서도 **단일 writer**다. `graph.db`의 유일한 기록자는 `127.0.0.1`에 바인드된 로컬 데몬이다. Confluence 같은 외부 도구는 사본을 받는다. 양방향 동기화를 포기한 대신 충돌 해소 문제를 통째로 없앴다. 발행은 스펙 해시로 멱등이다. 같은 스펙이면 아무것도 보내지 않고, 수정됐으면 기록된 페이지를 갱신하고, 처음이면 하나 만든다. DDL은 `schema/schema.sql` 한 파일에만 있고, 런타임과 계약 테스트가 같은 파일을 읽는다. **런타임과 테스트가 서로 다른 스키마를 보고 있을 수 없다**는 것을 파일 배치로 보장한 셈이다.

대가는 분명하다. 데몬이 없으면 앱은 `localStorage` 임시 모드로 떨어지고, LLM 제안·발행·SQLite 저장은 동작하지 않는다. 정적 데모에서는 제안이 로컬 규칙 폴백으로 답하고, 배지가 그렇게 말한다. 두 사람이 같은 프로젝트를 동시에 편집하는 것도 지원하지 않는다. 대신 "지금 보고 있는 것이 원본인가, 사본인가"라는 질문이 제품에서 사라진다.

## 3. 원칙 2 — 데몬 하나, 표면은 얇게

표면이 6개(CLI, 웹, 데스크톱, 텔레그램, 디스코드, 슬랙)고 백엔드가 9개면, 각 표면이 각 CLI를 직접 붙이는 순간 54개의 어댑터가 생긴다. 그리고 세션·권한·히스토리가 표면마다 따로 논다. 한 표면에서 시작한 턴을 다른 표면에서 이어받을 수 없다.

그래서 `damond` 하나가 세션, 저장, 권한, 채널, 릴레이를 소유하고, 모든 클라이언트는 JSON-RPC v2 over WebSocket의 얇은 클라이언트가 된다. 이건 한 번에 정한 구조가 아니다. LLM provider 직결기, ACP 표준 프로토콜기, native CLI 백엔드기를 거쳤고, 세 번의 방향 전환에서 살아남은 것은 데몬 중앙 구조 하나였다. v2 재설계에서 카탈로그를 19개에서 3개로 줄였고, 지금은 9개다.

카탈로그에 들어올 수 있는 CLI에는 조건이 있다. **토큰 스트리밍, 턴 중 권한 질문, 중단**을 native 양방향 프로토콜로 지원해야 한다. 되는 것만 넣는다. 카탈로그는 기능 목록이 아니라 보증 목록이다.

백엔드는 세 계열로 정규화된다. `stream-json`(Claude Code, Qwen Code), NDJSON app-server(Codex, Droid, ZCode, Oh My Pi, Pi), HTTP+SSE(OpenCode, MiMo). 계열마다 트랜스포트가 다르고, 계열 위의 dialect가 프레임을 `StreamEvent` 하나로 번역한다. 데몬 위쪽은 자기가 어떤 CLI와 말하는지 모른다.

한 턴의 실제 순서는 이렇다.

```
GET  /health                     → status · version · backends
POST /v1/ws_ticket               → ticket (60초 · 1회용)
GET  /ws?ticket=…                → 업그레이드
     ← hello  { protocol: 2, supported[], capabilities, methods }
     → turn.start { sessionId, prompt, idempotencyKey }
     ← session.event · timeline.assistant_message   (델타 1개)
     ← session.event · timeline.tool_call
     ← session.event · permission_requested { kind: tool | question | plan }
     → permission.respond { requestId, action }
     ← session.event · permission_resolved
```

권한 요청이 어느 화면으로 흘러가야 하는지는 서버가 정하지 않는다. 그 턴을 보고 있는 클라이언트가 받는다. 턴 중 권한 질문을 임의의 연결된 클라이언트로 push하고 `permission.respond`로 되돌리려면 pending ask의 소유자가 중앙에 있어야 한다. 중앙화의 실질적 이유가 이것이다.

`EventJournal`은 최근 이벤트를 2048개까지 들고 있다가 늦게 붙은 구독자에게 재생한다. 그래서 클라이언트는 상태 없이 붙었다 떨어져도 되고, 다른 표면이 진행 중인 턴을 이어받을 수 있다. 메서드는 `domain.verb` 형식으로 114개다. 표면이 늘어도 프로토콜은 하나다.

**데몬은 에이전트의 자격증명을 쥐지 않는다.** 각 CLI의 로그인을 그대로 쓴다. 이건 편의 기능이 아니라 경계 결정이다. 데몬이 키를 대행하면 데몬이 곧 유출 표면이 된다. 대가는 "설치된 CLI가 로그인돼 있어야 한다"는 제약이고, 이 제약은 README 첫 문단에 그대로 써 있다.

인증은 세 겹이다. loopback + 토큰 없음이면 개방. 그 외에는 `Authorization: Bearer` 또는 60초·1회용 WS 티켓이다. 쿼리스트링 토큰은 거부한다. 로그와 프록시에 남기 때문이다. non-loopback 바인드에서 토큰을 해석하지 못하면 **부팅을 거부**한다(fail-closed). 열린 채로 뜨는 것보다 안 뜨는 게 낫다.

원격은 relay로 나간다. 클라이언트가 X25519 임시 키를 교환하고, **클라이언트가 먼저** `sha256(token ‖ client_pub ‖ daemon_pub)`을 증명한다. 데몬이 먼저 증명하면 미인증 피어에게 토큰 유도물을 노출하기 때문이다. 이후 프레임은 방향 분리 키의 AES-256-GCM이고, 시퀀스 번호가 AEAD nonce 겸 replay 방지다. 등록 secret은 첫 프레임 바디로 보내고 URL 쿼리에는 넣지 않는다.

남은 위험도 코드 헤더에 적혀 있다. 저엔트로피 `auth_token`은 캡처된 핸드셰이크 하나로 오프라인 무차별 대입이 가능하다. 대응은 고엔트로피 토큰, `wss://`, 그리고 opt-in KDF 스트레칭(2^16 라운드, 자동 협상, 구형 피어는 단일 해시로 폴백)이다. 보안 문서에 "해결됨"이라고 쓰지 않고 "잔여 위험과 완화"로 쓰는 쪽을 택했다. 그게 정확하기 때문이다.

### 왜 클라우드 서버가 없는가

중간 서버가 하던 일은 세 가지다. 세션 유지, 인증, 히스토리. 셋 다 로컬에서 끝난다. 서버를 두면 (1) 사용자의 코드와 대화가 내 서버를 지나간다는 신뢰 문제, (2) 운영비, (3) 왕복 지연이 생긴다. 브라우저가 `127.0.0.1:9470`과 직접 말하면 셋이 동시에 사라진다.

대가는 브라우저에서 loopback 데몬으로 붙는 제약이다. origin 검사, 티켓 인증, 그리고 원격 접속이 필요할 때만 relay. 여기에 단일 장애점도 받아들인다. 데몬이 죽으면 모든 표면이 끊긴다. 히스토리가 한 곳에 모이고 권한 게이트가 하나가 되는 것과 맞바꾼 대가다. 이걸 숨기지 않고 ADR에 "데몬은 단일 장애점이다"라고 적어 두었다.

## 4. 원칙 3 — 증거 없는 자동화는 자동화가 아니다

세 번째 원칙은 앞의 두 원칙을 지키는 장치다. 로컬 원천은 조용히 썩고, 데몬의 계약은 조용히 깨진다. 막는 건 테스트뿐이다.

### 4.1 파이프라인: 골든케이스와 슬롭 린트 — assignment-map

채용 과제·해커톤·공모전을 매일 03:00 KST에 수집해서, AI로 제출 가능한 것만 남기는 파이프라인이다. 여기서 신뢰할 수 있는 건 수집량이 아니라 **판정의 재현성**이다.

- **골든케이스 6개**(채용 4 + 이벤트 2)를 고정 기대값으로 둔다. 회사명 포함 여부, AI 정책 판정, 채용 연계 여부. merge 후 검증이 이 케이스를 재현하지 못하면 **커밋을 잠근다.** 케이스가 시대에 뒤처지면 데이터가 아니라 케이스 파일을 먼저 고치고 사유를 커밋한다.

기대값은 코드가 아니라 데이터다. 판정이 흔들리면 케이스가 아니라 수집기가 틀린 것이고, 그래서 이 파일을 고치려면 사유를 커밋해야 한다.

```json
{ "id": "seed-kr-01",
  "expect": { "company_includes": "올리브영", "ai_policy": "required" } }
```

이 파이프라인의 게이트는 두 개다. 수집 직후의 검증(골든케이스)과 빌드 직전의 린트(슬롭 체크). 하나가 실패하면 데이터는 커밋되지 않고, 다른 하나가 실패하면 사이트는 배포되지 않는다.

- **안티슬롭 16체크**가 빌드에 내장되어 있다. `gradient()`, `background-clip: text`, Inter/Roboto/Geist/system-ui 선행 폰트, `backdrop-filter`/`text-shadow`, 이모지, `letter-spacing ≥ 0.1em` eyebrow, 스톡 카피 6단어, fade-up 스크롤 리빌, `text-align: center` 히어로, `border-radius > 4px`, `" · "` 구분자, card/hero/glass 클래스명. 그리고 양성 체크 4개(`:focus-visible`, `prefers-reduced-motion`, viewport, `img alt`). 하나라도 걸리면 build가 exit 1로 끝나고 배포가 멈춘다.

이 체크들은 취향을 강제하지 않는다. **AI가 만든 티가 나는 지점**을 고정해 둔 것이다. 취향은 사람이 정하고, 티나는 패턴은 기계가 막는다. 데이터는 채용 60건, 이벤트 165건(2026-11-21 수집 기준)이고, 26시간 넘게 갱신이 없으면 watchdog이 이슈로 경보를 낸다. 운영비는 0원이다.

### 4.2 스트리밍 UI: 발화를 센다 — livesay

스트리밍 답변을 `aria-live`에 토큰 단위로 밀어 넣으면 DOM은 맞고 사용자는 틀린다. 이걸 "접근성 이슈"라고 부르면 아무것도 바뀌지 않는다. 숫자로 부르면 바뀐다. 같은 78단어 답변, 같은 속도, 같은 시뮬레이터(`nvda-like`)로 잰 값이다.

| | 순진한 스트리밍 | `createStreamingAnnouncer` |
| --- | --- | --- |
| live-region 갱신 | 78회 | 2회 |
| 초당 최대 갱신 | 36회/s | 2회/s |
| 발화 수 | 7회 | 4회 |
| 완료 안내 | 없음 | 있음 |
| 발견된 문제 | 3건 | 0건 |

두 페이지 모두 저장소에 있고, 이 동작이 CI에서 매번 단언된다. 규칙은 계약으로 쓴다. `token-storm`(live region이 1초에 5회 이상 갱신), `silent-completion`(끝을 알리지 않음), `silent-abort`(실패 후 조용함), `assertive-abuse`(답변당 1회 초과), 중복 발화, 부분 발화.

AT마다 동작이 다르기 때문에 리포트는 항상 **simulated**라고 쓴다. `nvda-like`, `voiceover-like`, `spec-strict` 세 프로필로 같은 녹음을 재생한다. 특정 스크린리더의 정답을 맞히는 게 목적이 아니라, 어떤 프로필에서도 무너지지 않는 계약을 찾는 게 목적이다.

### 4.3 비결정성 위의 불변식 — agent-ui-guard

에이전트 채팅 UI의 버그는 시간적이다. 다이얼로그 두 개가 40ms 동시에 열렸다가 닫히고, 툴콜 스피너가 자기 턴보다 오래 살고, 5xx를 UI가 삼킨다. 그 40ms 동안 사용자는 막히고, 클릭 스크립트는 통과한다.

그래서 스크립트 대신 속성을 단언한다. `always`(모든 스텝 후 성립)와 `eventually`(기한 내 성립). 내장 불변식은 5개다: `singleModalAtATime`, `noStuckStreaming`, `toolCallBalanced`, `noConsoleOrPageErrors`, `noHttp5xx`. 가중 랜덤 액션으로 앱을 두드리고, 위반하면 `trace.json`, `report.md`, 스크린샷, 그리고 바로 실행 가능한 `repro.spec.ts`를 남긴다. 버그를 찾는 것보다 중요한 건, 찾은 버그가 재현 가능한 테스트로 남는다는 점이다.

### 4.4 리뷰의 증거 — proofshot

AI가 만든 PR은 산문으로 자신을 설명한다. 리뷰어가 알아야 하는 건 하나다. **지금 어떻게 보이고, 나빠졌나.** 두 빌드 디렉터리(또는 두 URL)를 주면 diff에서 라우트를 추론하고, 데스크톱/모바일 풀페이지를 캡처하고, `pixelmatch`로 변경 픽셀 비율을 내고, a11y 델타를 전/후로 같이 낸다. alt 없는 이미지, 이름 없는 버튼, 라벨 없는 필드, 헤딩 점프, 중복 id, `lang` 누락. 리포트는 안정 마커로 시작해서 워크플로가 이전 코멘트를 갱신한다. Storybook 스토리를 쓰지 않는 이유는 단순하다. PR이 건드린 페이지에는 스토리가 없다.

### 4.5 모델 출력의 게이트 — spec-studio eval

모델이 만든 제안은 결정 카드 하나로 접수되고, 채택 전에는 아무것도 쓰지 않는다. 그 카드의 품질을 5개 지표로 채점한다.

| 지표 | 의미 | 임계값 |
| --- | --- | --- |
| 스키마 | 제안이 프로토콜 스키마로 파싱되고 노드가 있음 | 100% |
| 타입 | 기대 노드 타입 재현율 | ≥ 85% |
| 링크 | 기대 링크 타입 재현율 | ≥ 85% |
| 핀근거 | 기대 핀 인용 재현율 | ≥ 90% |
| 근거비율 | 핀에 근거한 초안 / 전체 초안 | ≥ 90% |

한국어 골든케이스 30개(정책 10, 표/계약 10, 예외 10)를 규칙 폴백과 실제 모델이 **같은 케이스**로 푼다. 그래서 비교가 정직해진다. 폴백이 0%인 hard case 3개는 live가 움직여야 할 목표로 남겨 두었다. 연구 브리프 10케이스는 인용 정확성 100%(환각 인용 0)와 마커 정확도 ≥ 90%로 따로 채점한다. 임계값을 못 넘으면 명령이 non-zero로 끝난다. CI는 시크릿 없이 mock으로 돌고, 키를 export한 개발자는 같은 케이스로 live를 잰다.

게이트는 느리고, 창의성을 재지 못하고, 틀릴 수 있다. 그래서 역할을 좁혔다. **게이트는 "나빠졌는가"만 판정한다. "좋은가"는 사람이 정한다.** 게이트가 틀리면 코드가 아니라 케이스를 먼저 고치고, 왜 고쳤는지 커밋에 남긴다.

게이트는 명령 하나로 끝난다. `pnpm check`가 타입체크 → eval 타입체크 → 단위 테스트 → 골든셋 eval → 빌드 → 의존성 검사 → 스키마 계약을 순서대로 돌리고, CI는 이 명령만 실행한다. 사람이 기억해야 할 게이트가 여러 개면 그중 하나는 반드시 빠진다.

## 5. 세 원칙은 서로를 지탱한다

원칙 1은 데이터의 위치를 정하고, 원칙 2는 그 데이터를 쓰는 유일한 주체를 정하고, 원칙 3은 그 주체의 계약을 고정한다. 순서를 뒤집으면 성립하지 않는다. 데몬을 먼저 만들면 검증할 원천이 없고, 게이트를 먼저 만들면 지킬 계약이 없다.

그리고 원칙 3이 없으면 1과 2는 조용히 썩는다. 링크 타입이 조용히 깨지는 걸 막은 건 리뷰가 아니라 트리거였고, 발행이 같은 페이지를 두 번 만드는 걸 막은 건 규율이 아니라 스펙 해시였다.

무엇을 잃었는지도 적어 둔다.

- **의미 검색의 유연성.** 그래프는 구조만 답한다. 자연어로 "이게 뭐 하는 코드야"를 물으면 못 찾는다.
- **무설치 경험의 일부.** 데몬이 필요하다. 정적 데모는 축소판이고, 그 축소판은 스스로 그렇게 말한다.
- **다중 사용자 동시 편집.** 단일 writer, 단일 파일. 협업은 범위 밖이다.
- **데몬 단일 장애점.** 데몬이 죽으면 모든 표면이 끊긴다.
- **"그럴듯한 데모"를 빨리 만드는 속도.** 게이트를 붙이는 순간 데모는 느려진다. 대신 배포 후에 조용히 틀리는 일이 줄어든다.

## 6. 이 원칙을 적용할지 판단하는 체크리스트

1. **답에 좌표가 필요한가?** 필요하면 그래프다. 좌표가 없어도 되는 탐색이면 임베딩이 더 유연하고 더 빠르다.
2. **구조를 기계가 아는가, 의미만 사람이 아는가?** 코드, 스펙 문법, 링크처럼 구조가 명시된 데이터는 결정적으로 답할 수 있다. 의미 판단이 본질이면 결정적 그래프는 답이 아니다.
3. **상태를 공유해야 하는 표면이 둘 이상인가?** 그렇다면 중앙 소유자가 필요하다. 하나라면 클라이언트 상태로 충분하고, 데몬은 과하다.
4. **실패가 조용한가?** 조용한 실패(스트리밍 UI, 정책 판정, 코드 그래프, 접근성)에는 제품보다 계측을 먼저 붙인다.
5. **이 결정을 되돌릴 수 있는가?** 단일 파일, 사본, 마이그레이션 경로가 있으면 되돌릴 수 있다. 없으면 되돌릴 수 있는 형태로 먼저 만든다.
